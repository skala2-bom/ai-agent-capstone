# 입고 지연 → 생산계획 부분 저장 → 남은 구매 문제 해결

2026-10-23 · `rag` 구현 및 최신 `main` 병합 검증 기록. DB 테이블 구조 변경 없음.

## 1. 이번에 바꾼 동작

| 문제 | 원인 | 변경 | 결과 |
|---|---|---|---|
| PP-03을 미뤄 릴레이 문제를 해결해도 MCU 부족이 남아 생산계획 저장이 막힘 | 생산 요청 전체 문제가 해소돼야 확정할 수 있었음 | 요청 문제를 일부 줄이고 다른 결품·과잉을 악화시키지 않는 변경은 먼저 저장 | `PARTIALLY_COMPLETED`: 생산계획 저장 완료 · 구매 문제 남음 |
| 저장한 생산계획과 남은 구매 문제가 구분되지 않음 | 기존 구매 인계는 미저장 생산 whatif를 발주와 함께 실행하는 구조 | 현재 DB를 다시 계산해 남은 요청 범위만 별도 구매 요청으로 생성 | 생산계획 재적용 없이 남은 구매 문제만 해결 |
| 구매 요청이 반려되면 원래 요청의 상태가 불명확 | 생산 저장·후속 구매의 처리 시점이 달라짐 | 연결된 구매 요청 완료 시 원래 요청도 완료, 반려·취소 시 부분 처리 상태로 복귀 | 먼저 저장한 생산계획 유지, 반려 사유 확인·재검토 가능 |
| 결품 답변 뒤에 ‘문제가 없습니다’가 붙음 | 모델의 요약 문장을 그대로 사용 | 결품·주의·과잉 수와 새 발주 가능 여부는 계산 결과로 요약 | 요약과 상세 목록의 모순 차단 |
| ④에서 관련 없는 발주의 날짜·수량을 추가로 요구 | 현재 DB 반영 요청을 별도 변경 조건의 누락으로 해석 | 분류 프롬프트에 현재 표 사용과 과거 기준일/새 입고일 구분 명시 | 실제 모델 재검증에서 PO-2609-008의 12/25 변경 한 건으로 분석 |

이미 저장한 생산계획을 다시 미저장 whatif로 보내는 경로도 차단했다. 구매→생산 연결 질문에서는 **이 생산계획 변경안 검토 →**를 통해 먼저 검토·저장하고, 요청함에서 남은 문제를 전달한다. 일반 생산관리의 독립적인 생산→구매 요청은 기존처럼 사용할 수 있다.

## 2. 시연 질문과 클릭 순서

새 시드 데이터 기준이다. 실행한 데이터로 다시 시연하면 결품량·추천 발주가 달라질 수 있다. 계정은 `buyer`(박구매), `planner`(김계획), `approver`(팀장), 시드 비밀번호는 `1234`다.

### ① 구매: 분석 후 생산팀에 요청

**1-A. 장기화 비교 — 분석용 가정**

> 세미온반도체 공장 화재로 MCU 발주 PO-2609-008의 입고가 약 1주 늦어질 수 있다고 합니다. 릴레이 발주 PO-2610-106도 11월 27일로 늦어집니다. 두 지연을 함께 분석하고, MCU 지연이 장기화되면 어디부터 생산 차질이 생기는지도 보여 줘.

확인: 두 발주 동시 분석, MCU 1·4·12주 비교, 통보 기준 결품은 릴레이 1,000개(PP-03), MCU 500개(PP-04). 장기화 비교는 대비 가정이다.

**1-B. 협력사가 확정한 날짜로 생산 요청 — ‘새 대화’ 후 입력**

> 협력사에서 입고일 변경을 확정 통보했습니다. MCU 발주 PO-2609-008은 2026년 11월 27일에서 12월 4일로, 릴레이 발주 PO-2610-106은 2026년 11월 20일에서 11월 27일로 늦어집니다. 현재 생산계획에 어떤 결품이 발생하나요?

1. **생산팀에 일정 조정 요청** 클릭.
2. ‘지연 사유’에 협력사 통보 내용 작성.
3. ‘요청 내용’ 예: `PP-03 600대의 생산일을 11/28로 조정 가능한지 검토해 주세요. 남은 MCU 문제는 구매팀에서 후속 대응하겠습니다.`
4. 변경 전후 날짜 확인 후 동의 체크.
5. **지연 사실 반영 및 생산팀에 전송** 클릭.

이 시점에 두 입고일과 변경 이력이 저장된다. 생산 요청은 `접수 대기`로 전달된다.

### ② 생산관리: 먼저 저장하고 남은 문제 전달

1. 김계획 로그인 → **부서 요청함**(또는 상단 부서 알림)에서 구매 요청 선택.
2. **내가 담당하기** → **AI에게 생산 변경안 묻기** 클릭.
3. 아래 질문 전송.

> 현재 저장된 입고 일정을 기준으로, 벽스위치 PP-03의 생산일을 2026년 11월 23일에서 11월 28일로 옮기면 어떤 문제가 남나요? 수량은 600대로 유지합니다. 릴레이 결품이 해소되는지, 다른 생산에 새 결품이 생기는지, MCU 부족은 어디에 남는지 확인해 주세요.

4. 답변의 **이 생산계획 변경안 검토 →** 클릭.
5. PP-03 날짜 `2026-11-28`, 수량 `600` 확인 → **변경안 검증**.
6. 릴레이 결품 해소·남은 PP-04 MCU 500개 확인. 변경 사유 작성.
7. **생산계획 먼저 저장** → 확인 팝업의 **생산계획만 저장**.
8. 요청 상태 **생산계획 저장 완료 · 구매 문제 남음** 확인.
9. **남은 문제를 구매팀에 요청** 클릭.
10. ‘현재 남은 문제’에 MCU만 있는지 확인하고 전달 내용 작성 → **구매팀에 남은 문제 전송**.

전달 내용 예:

> PP-03 생산일을 11/28로 저장했습니다. 남은 11/30 PP-04의 MCU 500개 부족만 기존 발주 당김이나 분할로 해결해 주세요. 협력사 확약과 다른 제품에 미치는 영향도 확인해 주세요.

7번에서 생산계획이 실제 저장된다. 10번은 그 계획을 다시 바꾸는 요청이 아니라 **남은 구매 문제를 해결하는 요청**이다. 원래 요청은 `연결된 구매 요청 검토 중`으로 바뀐다.

### ③ 구매·팀장: 남은 MCU 문제 해결

1. 박구매 → **부서 요청함** → 새 생산→구매 요청 → **내가 담당하기**.
2. **AI에게 해결 방법 묻기**에서 아래 질문 전송.

> 현재 저장된 생산계획은 유지하고, 이 요청의 남은 MCU 부족을 기존 발주 당김이나 분할로 해결해 줘. 세미온 계약 근거와 다른 제품에 미치는 영향도 보여 줘.

3. AI 제안 확인 → 전체 문제 설명·개인 메모 작성 → **팀장에게 승인 요청**.
4. 팀장 → **승인 대기함** → **승인 상세** → **승인** → 팝업의 **검토 완료**.
5. task의 **승인 및 실행** → **전체 승인 및 실행**.
6. 실행 전 최신 데이터·저장된 생산계획·원래 요청 문제를 재검증. 통과하면 발주 변경과 상태·이력을 한 트랜잭션으로 반영.
7. 원래 생산 요청과 후속 구매 요청 모두 `처리 완료`. PP-03은 이미 저장한 11/28 그대로 유지.

**추천안은 실제 검증 결과로 확인한다.** main 병합 전 첫 실행에서는 `PO-2609-008`의 800개 전체를 12/4→11/30로 당기는 안이 선택됐다. 사용자가 제시한 `PO-2609-001` 500개 당김과는 다른 안이다. 화재 때문에 PO-2609-008을 당길 수 없다면 그 안을 승인해서는 안 되며, 실제 협력사 가능 여부에 맞춰 수정 필요·재검토를 진행해야 한다. 최신 main 병합 후 재검증에서는 PO-2609-001 500개를 12/12→11/30로 당기는 안과 CT-SUP01 2.1조 근거가 나왔다. 협력사 확약은 시연 가정이며 외부 협력사 시스템과 연결한 결과가 아니다.

### ④ 구매: 실행한 상태에서 장기화 재분석

현재 DB를 기준으로 독립 분석하려면 **새 대화** 후 입력한다.

> 현재 DB에 저장된 생산계획과 실행된 발주 변경을 기준으로 다시 분석해 줘. 세미온의 MCU 발주 PO-2609-008이 원래 예정일 2026년 11월 27일 기준 총 4주 지연되어, 새 입고일은 2026년 12월 25일이라고 합니다. 이 발주 입고일만 12월 25일로 가정하면 현재보다 어느 생산계획에서 MCU 결품이 새로 생기나요?

현재 저장된 입고일에 ‘4주 더’를 더하지 않도록 **새 입고일 12/25**를 명시한다. 분석만으로 발주·생산계획은 바뀌지 않는다.

main 병합 전 첫 실행의 결과: PO-2609-008을 다시 12/25로 늦추므로 PP-04 MCU 500개 부족이 재발하고 PP-05 MCU 400개 부족이 발생했다. main 병합 후에는 PO-2609-001을 먼저 당겨 실행했으므로 PP-04 결품은 없고, PP-05 MCU 400개 부족만 발생했다.

## 3. 상태·권한·저장 계약

| 시점 | 원래 구매→생산 요청 | 후속 생산→구매 요청 | 저장 데이터 |
|---|---|---|---|
| 구매 확정 지연 전송 | OPEN | 없음 | 확정 입고일·이력 |
| 생산 담당 접수 | IN_PROGRESS | 없음 | 담당자 |
| 생산계획 먼저 저장 | PARTIALLY_COMPLETED | 없음 | 계획·변경 이력·남은 문제 스냅샷 |
| 남은 문제 전송 | WAITING_LINKED | OPEN | 현재 DB에서 다시 계산한 남은 문제 |
| 구매 검토 후 승인 요청 | WAITING_LINKED | WAITING_REVIEW | 승인 대기 카드 |
| 팀장 전체 실행 성공 | COMPLETED | COMPLETED | 발주·승인·변경 이력 |
| 구매 요청 최종 거절/전체 취소 | PARTIALLY_COMPLETED | REJECTED / CANCELLED | 먼저 저장한 생산계획 유지·반려 사유 |

- `plan-preview` 응답에 `partial`, `remainingImpact` 추가. 기존 `canExecute`는 부분 저장 가능 여부도 포함.
- `GET /api/coordination/requests/{id}/remaining-preview`: 담당 생산관리자만 최신 잔여 문제·업무 fingerprint·요청 revision 조회.
- `POST /api/coordination/requests/{id}/remaining-request`: `commandId`, `expectedRevision`, `expectedFingerprint`, `message` 필요. 동일 명령 재전송은 같은 요청 반환.
- 후속 요청 `requestKind=REMAINING`, `planOps=[]`, `planChanges=[]`, `appliedPlanChanges`에 이미 저장한 계획 기록. 원래 요청은 `remainingAnalysis` 보관.
- Agent는 서버가 전달한 `issueScope`의 남은 문제만 해결 대상으로 삼는다. 안전 검증에는 다른 계획의 결품·과잉도 유지.
- 팀장 실행은 현재 저장된 계획과 변경 후 전체 영향 재검증. 이미 저장한 계획을 다시 적용하지 않음.
- 새 DB 테이블·컬럼 없음. 기존 `ai_task`, `task_event`, `change_history` 사용. 후속 요청의 원본 task는 시스템 계산 스냅샷이며, 구매 해결 작업은 별도로 실제 LLM을 호출함.

## 5. 검증과 한계

- 병합 전 회귀: **백엔드 80건, Python 126건(일반 91 + Agent 35), 프론트 62건 통과**, TypeScript 검사·프론트 프로덕션 빌드 통과.
- 사용자 개발 환경 `ai-agent-capstone`과 별도인 `capstone-demo-flow`에서 실제 API·DB·RabbitMQ·MCP·OpenAI·Chrome으로 검증.
- RAG 문서 6개를 실제 임베딩으로 색인. 구매·생산·팀장으로 각각 로그인해 버튼을 클릭하고 저장 전후 API/DB 값 확인.
- 생산 저장 확인 팝업 취소 시 미변경, 저장 후 구매 발주 미변경, 새로고침 후 부분 상태 유지, MCU만 전달, 검토 체크만으로 발주 미변경, 실행 팝업 취소 시 미변경, 전체 실행 후 양쪽 요청 완료 확인.
- Java 테스트로 권한·중복 전송/실행·검토 후 데이터 변경·저장된 계획 변경·반려 후 부분 상태 복귀·계획 이력 1건 유지 확인.
- 최종 실제 DB 이력: 확정 입고 변경 2건 + PP-03 생산 변경 1건 + 승인 발주 변경 1건. ④는 분석만 수행해 이력 추가 없음. 첫 시도에서 ④ 분류 오류를 재현해 프롬프트를 보완한 뒤 재검증. 테스트 스크립트의 초기 영향/실행 후 영향 구분 오류도 수정해 `post_execution_impact`로 결품 해소를 확인.
- 정상 Maven Docker 재빌드는 Central 의존성 조회 실패, 로컬 패키징은 archiver 플러그인 클래스 누락으로 실패. 이번 E2E는 기존 테스트 이미지 JAR의 애플리케이션 클래스만 최종 `mvn test` 컴파일 결과로 교체해 실행함. 라이브러리 버전·Dockerfile은 변경하지 않음. **정규 Docker 재빌드 성공 검증과 구분해야 함.**
- 기존 후보 생성기는 협력사 화재 같은 자연어 사정을 납기 변경 불가 제약으로 자동 확정하지 않음. 추천안의 실제 이행 가능 여부는 사람이 확인해야 함.
- 병합 전 첫 해결안의 근거에는 납기 당김 조항 대신 계약기간·MOQ 조항이 포함됨. main의 협력사별 당김·분할 검색 개선을 병합한 뒤 이 시나리오에서는 CT-SUP01 2.1조가 첫 근거로 나옴. 외부 협력사의 실제 확약이나 모든 질문의 검색 적합성을 검증한 것은 아님.
- 기간 비교는 기존 1·4·12주 구현을 사용. 이번 작업에서 임의 기간 추천 기능을 추가한 것은 아님.
