# 결정 기록 (Decision Log)

> **목적**: 무엇이 정해졌는지, **왜 그렇게 정했는지**를 남긴다. 뒤에 합류한 사람이 "이건 왜 이렇게 돼 있지?"를 코드만 보고 추측하지 않게 하는 것이 목적이다.
>
> **읽는 법**: 각 항목은 `결정 → 근거 → 고려했다 버린 안 → 뒤집을 때 바꿀 곳` 순서다.
> **상태 표시**: ✅ 팀이 정함 · 🟡 **Claude가 판단함 (팀 확인 필요)** · ⬜ 아직 미정

## 1. 2026-10-20 오전 스크럼 — 팀이 정한 것

### 1.1 ✅ 안전재고는 부품마다 다르고, 담당자가 직접 입력한다

- 부품을 처음 등록할 때 담당자가 안전재고 수량을 임의로 정해 입력한다.
- → 품목 테이블에 `safety_stock` 칸이 생긴다. 계산식으로 자동 산출하지 않는다.

### 1.2 ✅ 결품 = 재고 0개 미만

- 어느 날짜든 예상 재고가 **0개 아래로** 내려가면 결품이다.
- 🟡 **Claude 판단**: "0 이상이지만 안전재고 미만"은 결품이 아니라 **경고(warning)** 로 돌려준다.
  - **근거**: 아키텍처 8.1의 `analyze_impact`가 이미 "결품·과잉·**경고**"를 돌려주게 돼 있다. 안전재고를 부품마다 따로 입력받기로 한 이상(1.1), 그 값이 쓰이는 자리는 경고뿐이다. 안전재고 미만을 결품으로 치면 발주를 당길 필요가 없는 건까지 승인 흐름을 타게 된다.
  - **뒤집으려면**: 안전재고 미만도 결품으로 본다면 backend analysis 모듈의 판정 한 줄만 바꾸면 된다.

### 1.3 ✅ 과잉 = 리드타임 기간에 쓸 양보다 재고가 많을 때

- 기준은 부품마다 다른 **리드타임**이다.
- 판정: `현재 재고 > (앞으로 리드타임 기간 동안의 소요량)` 이면 과잉.
- **왜 리드타임인가**: 리드타임은 "지금 주문해도 이만큼 기다려야 한다"는 기간이다. 그 기간에 쓸 양만큼은 쌓아 둬야 정상이고, 그걸 넘으면 묶인 돈이다.
- 버린 안: "필요일보다 리드타임 이상 일찍 입고되면 과잉" — 발주 단건을 보는 기준이라 재고 전체 수준을 못 본다. 스크럼에서 "각 부품마다 리드타임으로 기준"이라고 한 맥락은 재고 수준 쪽으로 읽었다.

### 1.4 ✅ 구매팀장은 구매팀원 권한을 모두 가진다

- 팀장 권한 = 팀원 권한 + 승인 권한. 역할이 상하 관계다.
- **따라오는 변경**: 아키텍처 10장의 "승인 요청 생성은 BUYER만" → **BUYER 또는 APPROVER**.

### 1.5 ✅ 팀장은 자기가 요청한 건을 자기가 승인한다

- 기존의 **"요청자 ≠ 승인자" 규칙을 없앤다.**
- ⚠️ **알고 넘어갈 것**: 이건 일반적인 내부 통제 원칙을 일부러 푸는 결정이다. 평가·발표에서 "승인 통제가 약한 것 아니냐"는 질문이 나올 수 있다.
  - 대비: 승인 기록에 `요청자 == 승인자`인 건을 **플래그로 남겨** 감사 추적이 되게 한다(테이블 칸 하나). 통제를 막는 대신 **기록으로 남기는** 방식이다. 🟡 Claude 제안.
- **그래도 지키는 것**: 승인 기록 없이는 backend가 발주 변경을 거부한다. 이 방어선은 그대로다.

### 1.6 ✅ 반제품은 만들지 않는다

- 완제품 ← 부품 2~3단계 구조를 유지한다. 중간 조립품 단계를 넣지 않는다.
- 아키텍처 문서가 이미 완제품·부품만 나누고 있어 **바꿀 것 없음**.

### 1.7 ✅ `approval.status`에서 `EXPIRED`를 뺀다

- 승인 대기에 만료 시간을 두지 않는다. 팀장이 승인하거나 거절할 때까지 기다린다.
- **따라오는 변경**: 아키텍처 4.2의 "승인 대기 24시간 → EXPIRED, 작업 CANCELLED" 줄과 12장 B5의 "승인 만료(현재 24시간)".
- 남는 상태: `PENDING → APPROVED | REJECTED → EXECUTED`

## 2. 🟡 비용 기반 사내 평가지표 (스크럼 2.4) — Claude가 설계함

> **스크럼 메모**: "비용에 따른 사내 평가지표 목데이터 만들고 / 구매팀에서 담당자가 검수 후 평가지표 입력 / 그걸 바탕으로 생산관리팀에서 우선순위 결정 / 비즈니스 mcp"
>
> 무엇을 평가하는지가 메모에 없어서 아래처럼 해석했다. **다르면 한 줄로 알려 주면 바꾼다.**

### 2.1 무엇을 평가하나: 협력사 × 부품

평가 대상을 **"이 부품을 이 협력사에서 받을 때의 비용·신뢰도"** 로 잡았다.

**그렇게 읽은 근거 3가지**

1. **"목데이터를 만들어 둔다"** — 매 요청마다 생기는 값이 아니라 **미리 쌓여 있는 표**라는 뜻이다. 대안(해결 방법)은 질문할 때마다 새로 만들어지므로 목데이터로 준비할 수 있는 대상이 아니다.
2. **"구매 담당자가 검수 후 입력"** — 구매팀이 검수하는 시점은 **입고 검수**다. 그때 알 수 있는 것은 "이 협력사가 납기를 지켰나, 품질은 어땠나"다. 즉 평가 대상은 협력사다.
3. **"비용에 따른"** — 단가·긴급 배송비·지연 패널티는 모두 **협력사 계약 조건**에서 나온다. 아키텍처 C3의 근거 문서 목록에도 "협력사 계약 조건(납기 변경 패널티·단가 구간)"이 이미 있다.

**버린 해석 2가지**

| 해석 | 버린 이유 |
|---|---|
| 해결 방법(대안) 자체를 평가 | 대안은 요청마다 새로 생겨서 "목데이터"와 "검수 후 입력"이 성립하지 않는다 |
| 제품·생산계획의 중요도를 평가 | 그건 생산관리팀이 정할 값인데, 메모에는 **구매팀이 입력**한다고 돼 있다 |

### 2.2 테이블 (제안)

`supplier_metric` — 협력사 × 부품 한 줄

| 칸 | 단위 | 누가 채우나 |
|---|---|---|
| `supplier_id`, `item_id` | – | 초기 목데이터 |
| `unit_price` | 원 | 계약 기준, 구매 담당자 |
| `expedite_cost_per_day` | 원/일 | 1일 당길 때 붙는 추가 비용. **"비용에 따른"의 핵심** |
| `delay_penalty` | 원 | 납기 지연 시 우리가 무는 패널티 |
| `on_time_rate` | % | **입고 검수 결과가 쌓이는 칸** |
| `quality_score` | 0~100 | 입고 검수 결과 |
| `evaluated_at`, `evaluated_by` | – | 언제, 어느 담당자가 입력했나 (감사 추적) |

### 2.3 흐름: 누가 넣고 누가 쓰나

```
구매 담당자 ──(입고 검수 후 화면에서 입력)──▶ supplier_metric 테이블
                                                    │
                                     backend 계산 서비스가 읽음
                                                    │
                                        compare_options 도구
                                                    │
                              대안별 추가 비용·결품 위험 숫자
                                                    │
                                      생산관리 담당자가 보고 우선순위 결정
```

### 2.4 🟡 중요한 판단: 평가지표 **입력은 AI 도구로 만들지 않는다**

- **조회**는 business-mcp 도구로 공개한다 (`get_supplier_metrics(item_id)`).
- **입력·수정은 사람이 쓰는 화면 API로만** 연다 (`PUT /api/suppliers/{supplier_id}/items/{item_id}/metrics`, 권한 BUYER).
- **근거**: 평가지표는 대안 비교의 **기준값**이다. AI가 이 값을 고칠 수 있으면, AI가 자기 추천을 통과시키려고 기준 자체를 바꾸는 길이 열린다. 채점 기준을 채점자가 고치는 셈이다. Harness Guardrails 관점에서 변경 도구를 승인으로 막는 것보다, **애초에 도구로 공개하지 않는 것**이 더 단순하고 확실하다.
- 교재의 "business_mcp 금지사항: 업무 규칙 복제"와 같은 결의 판단이다. 사람이 정하는 기준값은 AI 손이 닿는 곳에 두지 않는다.

### 2.5 뒤집을 때 바꿀 곳

| 바꾸는 내용 | 바꿀 곳 |
|---|---|
| 평가 대상이 협력사가 아니라면 | 이 절 전체 + 아키텍처 8.1 도구표 |
| 입력도 AI 도구로 열려면 | `destructive_hint = true`를 붙이고 승인 대상에 넣을 것 (2.4의 위험을 안고 가는 것) |

## 3. 🟡 분할 발주(`split_po`) 절차 — Claude가 설계함

> 도구 이름은 아키텍처 8.1에 이미 있었지만 **절차와 검사 규칙이 비어 있어** 아래처럼 채웠다.

### 3.1 무엇을 위한 기능인가

전체 수량을 다 당길 수는 없을 때 **급한 만큼만 떼어 먼저 받는다.**

예: MCU 500개가 11/30 입고 예정인데, 11/25에 100개가 급하다.
→ 500개를 **400개(11/30 그대로) + 100개(11/25)** 로 나눈다.

### 3.2 호출과 결과

```
split_po(po_id, split_qty, new_due_date, approval_id)
```

| 대상 | 수량 | 입고일 | 상태 |
|---|---|---|---|
| 원 발주 | 원래 수량 − `split_qty` | **그대로** | OPEN 유지 |
| 새 발주 | `split_qty` | `new_due_date` | OPEN, `parent_po_id` = 원 발주 ID |

- **떼어낸 쪽(새 발주)이 날짜를 옮긴다.** 원 발주는 건드리지 않는다.
  - 근거: 되돌리기가 쉽다. 잘못되면 새 발주만 취소하고 원 발주 수량을 되돌리면 된다. 원 발주 날짜까지 같이 바뀌면 복구할 상태가 두 배로 늘어난다.
- 새 발주 번호는 backend가 만든다. AI가 정하지 않는다.

### 3.3 검사 순서 (backend가 한다, 위에서부터)

| # | 검사 | 실패 시 오류 코드 | retry_hint에 넣을 것 |
|:-:|---|---|---|
| 1 | 원 발주가 `OPEN`인가 | `PO_NOT_OPEN` | 현재 상태 |
| 2 | `0 < split_qty < 원래 수량` | `INVALID_SPLIT_QTY` | 가능한 범위 (1 ~ 원래수량−1) |
| 3 | `new_due_date ≥ 오늘 + 리드타임` | `LEADTIME_INFEASIBLE` | **가장 빠른 가능일** |
| 4 | `new_due_date ≠ 원 발주 입고일` | `SPLIT_NOT_USEFUL` | 날짜가 같으면 나눌 이유가 없음 |

- 검사는 **전부 backend**에 있다. business-mcp는 오류 응답을 `ToolError` 한 문장으로 바꿔 던지기만 한다 (아키텍처 1.1 "규칙은 한 곳에").
- 3번의 retry_hint에 가장 빠른 가능일을 넣는 이유: 모델이 그 날짜를 읽고 **스스로 다시 호출**할 수 있다. 교재 2장의 "오류 메시지에 있는 상품 목록을 넣어 재호출하게 한다"와 같은 패턴이다.

### 3.4 🟡 중요한 판단: 분할할 때 MOQ는 다시 보지 않는다

- 나눈 뒤 각 발주가 최소 발주 수량(MOQ) 미만이어도 **통과시킨다.**
- **근거**: 협력사 입장에서는 같은 물량을 **나눠서 배송**하는 것이지 발주를 새로 받는 게 아니다. 합계는 그대로다. MOQ는 "이보다 적게는 만들어 줄 수 없다"는 생산 로트 기준이므로 합계로 판단하는 것이 맞다.
- **대신 생기는 비용**: 분할 배송에는 보통 수수료가 붙는다. → **협력사 계약 조건 문서(C3)에 "분할 배송 수수료" 조항을 넣고**, `compare_options`가 대안 비용에 더하게 한다. 막는 대신 **비용으로 드러내는** 방식이다.
- **뒤집으려면**: MOQ를 분할 후에도 검사한다면 3.3 표에 5번 검사를 추가하면 된다. 다만 그러면 "급한 100개만 당기기"가 MOQ 300개에 막혀 기능이 거의 안 쓰이게 된다.

### 3.5 승인 카드에 보여 줄 내용

```
PO-2609-001 (MCU 500개, 11/30)
  → PO-2609-001  400개  11/30  (그대로)
  → PO-2609-012  100개  11/25  (신규)
추가 비용: 긴급 300,000원 + 분할 배송 50,000원
```

- 사람이 **변경 전후를 한눈에** 봐야 승인 버튼을 누를 수 있다. 도구 이름과 인자만 보여 주면 판단이 안 된다.

### 3.6 범위 밖

- **분할 취소(되돌리기)는 만들지 않는다.** 필요하면 새 발주를 `cancel_po`로 취소하고 원 발주 수량을 `change_po_qty`로 되돌린다 (둘 다 승인 대상).
- 한 발주를 3개 이상으로 나누는 것: `split_po`를 두 번 부르면 된다. 전용 기능을 만들지 않는다.
