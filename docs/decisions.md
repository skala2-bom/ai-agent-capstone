## 1. 2026-10-20 오전 스크럼 — 확정

### 1.1 ✅ 안전재고는 부품마다 다르고, 담당자가 직접 입력한다

- 부품을 처음 등록할 때 담당자가 안전재고 수량을 임의로 정해 입력한다.
- → 품목 테이블에 `safety_stock` 칸이 생긴다. 계산식으로 자동 산출하지 않는다.
- 자동 산출하지 않는 이유: 담당자가 부품 특성(단종 위험, 협력사 안정성)을 보고 정하는 값이다.

### 1.2 ✅ 결품 = 예상 재고 < 0, 안전재고 미만은 경고

| 판정 | 조건 | 규칙 ID | 결과 |
|---|---|---|---|
| **결품** | `P(t) < 0` · 부족량 = `max(0, −P(t))` | INV-001 | 위험. 승인 흐름으로 이어진다 |
| **경고** | `0 ≤ P(t) < 안전재고` | INV-002 | 주의. 승인 흐름으로 가지 않는다 |

- `P(t)` = 시점별 예상 재고 = `초기재고 + t까지 누적 입고 − t까지 누적 생산소요` (수식 F-01)
- **안전재고 미만을 결품으로 치지 않는 이유**: 안전재고는 쓸 수 있는 재고다. 부족한 게 아니라 여유가 줄어든 상태다. 이걸 결품으로 치면 발주를 당길 필요가 없는 건까지 승인 흐름을 타게 된다.
- `P(t) = 안전재고`면 경고하지 않는다. 경계는 **미만**이다.
- 같은 날 결품과 경고가 겹치면 **결품만** 보여 준다. 중복으로 세지 않는다.

### 1.3 ✅ 과잉 = 고가 부품만, `max(리드타임, 30일)` 기간 소요량 초과

```
과잉량(t) = max(0, P(t) − 안전재고 − 앞으로 N일 동안의 소요량)
N = max(부품별 리드타임, 30)        … 기간은 t 다음 날부터
```

- 규칙 ID: INV-003. **고가 부품에만** 적용한다.
- **고가 부품만 보는 이유** (팀원 문서에서 가져옴): 싼 부품은 쌓여 있어도 묶인 돈이 적어서 경고할 가치가 없다. 경고가 많아지면 아무도 안 본다.

#### 왜 `max()`인가 — 스크럼과 기획안이 서로 달랐다

| 출처 | 과잉 관찰 기간 |
|---|---|
| 10/20 오전 스크럼 | 부품별 **리드타임** |
| 기획안 A1~A3 (팀원 문서가 "확정값"으로 인용) | **30일 고정** |

둘 중 하나를 고르면 각각 이런 문제가 생긴다.

**리드타임만 쓰면 → 골든셋이 깨진다.**
기획안의 정답 수치(SC2 케이스 과잉 300, SC3 구형 케이스 800)는 30일로 계산된 값이다. 케이스류 리드타임은 21일이라, 기간을 21일로 줄이면 향후 소요량이 줄고 **과잉량이 300보다 커진다.** 팀원 문서가 맨 앞에 "MUST PRESERVE — 새 규정 때문에 원래 판정이 바뀌지 않게 한다"고 못 박아 둔 것을 정면으로 어긴다. 이 정답 수치는 아키텍처 11장에서 기능 적합성 증빙으로 쓰기로 한 테스트다.

**30일만 쓰면 → 리드타임이 긴 부품이 오탐된다.**
리드타임이 8주(56일)인 부품은 56일치를 들고 있어야 정상인데, 30일 기준으로 보면 26일치가 과잉으로 잡힌다. 팀원 문서 Q2가 걱정하는 바로 그 오탐이고, 스크럼에서 "부품마다 리드타임으로" 하자고 한 이유도 이것으로 읽힌다.

**`max(리드타임, 30)`은 둘 다 만족한다.**

| 부품 | 리드타임 | N | 결과 |
|---|---|---|---|
| 스위치·도어센서 케이스 | 21일 | 30 | 기획안과 같은 값 → **골든셋 그대로 통과** |
| 리드타임 8주 부품 | 56일 | 56 | 56일치까지는 정상으로 봄 → **오탐 사라짐** |

읽는 법은 한 문장이다. **"최소 30일은 보되, 그보다 오래 걸려 들어오는 부품은 그 기간만큼 본다."**
30일은 바닥선이고, 리드타임이 그보다 길 때만 기간을 늘린다. 기간이 늘어나면 과잉량은 줄기만 하므로, 이 규칙이 30일 기준보다 과잉을 **더 많이** 잡는 경우는 없다.

#### ✅ 확인 결과 (10/20 오후, seed로 계산)

리드타임이 30일을 넘는 고가 부품 중 기획안 골든셋에 과잉 정답이 걸린 것이 **있었다.** SC3의 BLE 칩·홀 센서(8주) 800개다.
N = 56일로 보면 11/20 재고 1,400개가 12/14 허브 400 + 1/4 도어센서 800을 다 덮으므로 과잉이 0이 된다.
위에서 예고한 대로 **정답 쪽을 고쳤다** — 8주 걸려 들어오는 부품을 50일 들고 있는 것은 정상이다. 고친 정답은 7.3.

### 1.4 ✅ 구매팀장은 구매팀원 권한을 모두 가진다

- 팀장 권한 = 팀원 권한 + 승인 권한. 역할이 상하 관계다.
- **따라오는 변경**: 아키텍처 10장의 "승인 요청 생성은 BUYER만" → **BUYER 또는 APPROVER**.

### 1.5 ✅ 팀장은 자기가 요청한 건을 자기가 승인한다

- 기존의 **"요청자 ≠ 승인자" 규칙을 없앤다.**
- **감사 플래그는 두지 않는다** (10/20 확정). 시연에서 나올 시나리오가 아니고, 예외 상황을 넓히지 않기로 했다.
- **그래도 지키는 것**: 승인 기록 없이는 backend가 발주 변경을 거부한다. 이 방어선은 그대로다. 그리고 모든 승인 건에는 요청자·승인자·변경 전후·시각이 남는다 (규칙 AUD-001).

### 1.6 ✅ 반제품은 만들지 않는다

- 완제품 ← 부품 2~3단계 구조를 유지한다. 중간 조립품 단계를 넣지 않는다.
- BOM 전개는 **재고를 관리하는 구매 부품 단위**로 한다. 모듈과 그 안의 칩을 이중으로 더하지 않기 위해서다 (팀원 문서 F-02).

### 1.7 ✅ `approval.status`에서 `EXPIRED`를 뺀다

- 승인 대기에 만료 시간을 두지 않는다. 팀장이 승인하거나 거절할 때까지 기다린다.
- 남는 상태: `PENDING → APPROVED | REJECTED → EXECUTED`

## 2. ✅ 비용 기반 사내 평가지표 (스크럼 2.4)

> 무엇을 평가하는지가 스크럼 메모에 없어 Claude가 설계했고, 10/20에 **"가장 적합해 보이는 방향으로 가라"** 로 위임받아 확정했다.

### 2.1 무엇을 평가하나: 협력사 × 부품

평가 대상은 **"이 부품을 이 협력사에서 받을 때의 비용·신뢰도"** 다.

**그렇게 읽은 근거 3가지**

1. **"목데이터를 만들어 둔다"** — 매 요청마다 생기는 값이 아니라 **미리 쌓여 있는 표**라는 뜻이다. 대안(해결 방법)은 질문할 때마다 새로 만들어지므로 목데이터로 준비할 수 있는 대상이 아니다.
2. **"구매 담당자가 검수 후 입력"** — 구매팀이 검수하는 시점은 **입고 검수**다. 그때 알 수 있는 것은 "이 협력사가 납기를 지켰나, 품질은 어땠나"다.
3. **"비용에 따른"** — 단가·긴급 배송비·지연 패널티는 모두 **협력사 계약 조건**에서 나온다. 아키텍처 C3의 근거 문서 목록에도 "협력사 계약 조건(납기 변경 패널티·단가 구간)"이 이미 있다.

**버린 해석 2가지**

| 해석 | 버린 이유 |
|---|---|
| 해결 방법(대안) 자체를 평가 | 대안은 요청마다 새로 생겨서 "목데이터"와 "검수 후 입력"이 성립하지 않는다 |
| 제품·생산계획의 중요도를 평가 | 그건 생산관리팀이 정할 값인데, 메모에는 **구매팀이 입력**한다고 돼 있다 |

### 2.2 테이블

`supplier_metric` — 협력사 × 부품 한 줄

| 칸 | 단위 | 누가 채우나 |
|---|---|---|
| `supplier_id`, `item_id` | – | 초기 목데이터 |
| `unit_price` | 원 | 계약 기준, 구매 담당자 |
| `lead_time_days` | 일 | 이 협력사의 리드타임. **10/20 오후 추가** — 대체 협력사는 주 협력사와 리드타임이 달라서 `item`의 값 하나로는 못 쓴다 |
| `expedite_cost_per_day` | 원/(개·일) | 이미 낸 발주에서 **1개를 1일** 당길 때 붙는 추가 비용. **"비용에 따른"의 핵심**. 10/20 오후에 발주 1건 기준에서 바꿨다 (6.14) |
| `split_fee` | 원 | 발주 1건을 나눠 받을 때 한 번 붙는 수수료. **10/20 오후 추가** — 3.4의 분할 배송 수수료를 계산이 쓰려면 문서뿐 아니라 DB에도 있어야 한다 |
| `delay_penalty` | 원 | 납기 지연 시 우리가 무는 패널티 |
| `on_time_rate` | % | **입고 검수 결과가 쌓이는 칸** |
| `quality_score` | 0~100 | 입고 검수 결과 |
| `evaluated_at`, `evaluated_by` | – | 언제, 어느 담당자가 입력했나 |

### 2.3 흐름: 누가 넣고 누가 쓰나

```
구매 담당자 ──(입고 검수 후 화면에서 입력)──▶ supplier_metric 테이블
                                                    │
                                     backend 계산 서비스가 읽음
                                                    │
                                        compare_options 도구
                                                    │
                              대안별 추가 비용·결품 위험 숫자
                                                    │
                                      생산관리 담당자가 보고 우선순위 결정
```

### 2.4 ✅ 평가지표 **입력은 AI 도구로 열지 않는다** (10/20 확정)

- **조회**만 business-mcp 도구로 공개한다 (`get_supplier_metrics(item_id)`).
- **입력·수정은 사람이 쓰는 화면 API로만** 연다 (`PUT /api/suppliers/{supplier_id}/items/{item_id}/metrics`, 권한 BUYER).
- **근거**: 평가지표는 대안 비교의 **기준값**이다. AI가 이 값을 고칠 수 있으면, AI가 자기 추천을 통과시키려고 기준 자체를 바꾸는 길이 열린다. 채점 기준을 채점자가 고치는 셈이다. 변경 도구를 승인으로 막는 것보다, **애초에 도구로 공개하지 않는 것**이 더 단순하고 확실하다.
- 팀원 문서의 "LLM이 하지 않을 것" 목록과 같은 결의 판단이다.

## 3. ✅ 분할 발주(`split_po`) 절차

> 도구 이름은 아키텍처 8.1에 있었지만 **절차와 검사 규칙이 비어 있어** Claude가 채웠고, 10/20에 확정됐다.

### 3.1 무엇을 위한 기능인가

전체 수량을 다 당길 수는 없을 때 **급한 만큼만 떼어 먼저 받는다.**

예 (SC1, seed 기준): MCU 500개(`PO-2609-001`)가 12/12 입고 예정인데, 11/25에 100개가 급하다.
→ 500개를 **400개(12/12 그대로) + 100개(11/25)** 로 나눈다.

### 3.2 호출과 결과

```
split_po(po_id, split_qty, new_due_date, approval_id)
```

| 대상 | 수량 | 입고일 | 상태 |
|---|---|---|---|
| 원 발주 | 원래 수량 − `split_qty` | **그대로** | OPEN 유지 |
| 새 발주 | `split_qty` | `new_due_date` | OPEN, `parent_po_id` = 원 발주 ID |

- **떼어낸 쪽(새 발주)이 날짜를 옮긴다.** 원 발주는 건드리지 않는다.
  - 근거: 되돌리기가 쉽다. 잘못되면 새 발주만 취소하고 원 발주 수량을 되돌리면 된다. 원 발주 날짜까지 같이 바뀌면 복구할 상태가 두 배로 늘어난다.
- 새 발주 번호는 backend가 만든다. AI가 정하지 않는다.

### 3.3 검사 순서 (backend가 한다, 위에서부터)

| # | 검사 | 실패 시 오류 코드 | retry_hint에 넣을 것 |
|:-:|---|---|---|
| 1 | 원 발주가 `OPEN`인가 | `PO_NOT_OPEN` | 현재 상태 |
| 2 | `0 < split_qty < 원래 수량` | `INVALID_SPLIT_QTY` | 가능한 범위 (1 ~ 원래수량−1) |
| 3 | `new_due_date ≥ max(발주일 + 리드타임, 오늘 + 1일)` | `LEADTIME_INFEASIBLE` | **가장 빠른 가능일** |
| 4 | `new_due_date ≠ 원 발주 입고일` | `SPLIT_NOT_USEFUL` | 날짜가 같으면 나눌 이유가 없음 |

- 검사는 **전부 backend**에 있다. business-mcp는 오류 응답을 `ToolError` 한 문장으로 바꿔 던지기만 한다 (아키텍처 1.1 "규칙은 한 곳에").
- 3번의 retry_hint에 가장 빠른 가능일을 넣는 이유: 모델이 그 날짜를 읽고 **스스로 다시 호출**할 수 있다 (교재 2장 패턴).
- 3번의 기준이 "오늘"이 아니라 **그 발주의 발주일**인 이유는 7.2. (처음엔 `오늘 + 리드타임`이었는데, 그러면 SC1·SC4의 해결안이 전부 막혔다)
- 3번이 통과해도 **공급사가 확약한 것은 아니다.** 팀원 문서 Q5대로 "시간상 가능"과 "확정 납기"를 나눠서, 승인 전까지는 제안으로만 표시한다.

### 3.4 ✅ 분할할 때 MOQ는 다시 보지 않는다 (10/20 확정)

- 나눈 뒤 각 발주가 최소 발주 수량(MOQ) 미만이어도 **통과시킨다.**
- **근거**: 협력사 입장에서는 같은 물량을 **나눠서 배송**하는 것이지 발주를 새로 받는 게 아니다. 합계는 그대로다. MOQ는 "이보다 적게는 만들어 줄 수 없다"는 생산 로트 기준이므로 합계로 판단하는 것이 맞다.
- 재검사를 넣으면 "급한 100개만 당기기"가 MOQ 300개에 막혀 기능이 거의 안 쓰이게 된다.
- **대신 생기는 비용**: 분할 배송에는 보통 수수료가 붙는다. → 협력사 계약 조건 문서(C3)에 "분할 배송 수수료" 조항을 넣고, `compare_options`가 대안 비용에 더하게 한다. 막는 대신 **비용으로 드러내는** 방식이다.

### 3.5 승인 카드에 보여 줄 내용

```
PO-2609-001 (MCU 500개, 12/12)
  → PO-2609-001  400개  12/12  (그대로)
  → PO-2609-010  100개  11/25  (신규)
추가 비용: 긴급 340,000원 (100개 × 17일 × 200원) + 분할 배송 50,000원
```

- 사람이 **변경 전후를 한눈에** 봐야 승인 버튼을 누를 수 있다. 도구 이름과 인자만 보여 주면 판단이 안 된다.

### 3.6 범위 밖

- **분할 취소(되돌리기)는 만들지 않는다.** 필요하면 새 발주를 `cancel_po`로 취소하고 원 발주 수량을 `change_po_qty`로 되돌린다.
- 한 발주를 3개 이상으로 나누는 것: `split_po`를 두 번 부르면 된다.

## 6. 🟡 기술 결정 — Claude가 교재·평가표 기준으로 정함

> 2026-10-20에 **"교재와 평가 기준을 고려해 적절히 정해 달라"** 로 위임받았다. 지켜야 할 내용은 [contracts.md](contracts.md), 여기는 **왜 그렇게 정했는지**다.
>
> 배점 기준: MCP 20 · Harness 20 · Agent 설계 15 + 구현 15 · 아키텍처 10 · 인증 10 · 가산점 10

### 6.1 변경 도구는 금액과 무관하게 전부 승인 (B5)

- 금액 임계값을 두지 않는다.
- **근거**: 임계값을 두면 "이 금액 미만은 승인 없이 실행"이 생긴다. 교재는 "변경 도구 100% 승인"이라고 못 박았고, 평가표 Harness 20점의 Guardrails가 **승인 앞에서 멈추는 것**을 본다. 임계값 미만 건이 그냥 실행되는 순간 그 증빙이 약해진다. 규칙도 단순해진다.
- 버린 안: 금액 기준(예: 100만 원 이상만 승인) — 임계값을 정할 근거도 없고, 시연에서 득이 없다.

### 6.2 `whatif` 추출은 agent가, 시스템 작업만 backend가 (문서 모순 해소)

- 아키텍처 9.2는 backend가 `whatif`를 보낸다고 돼 있고, 5장은 agent의 `classify_intent`가 추출한다고 돼 있었다. 둘 다면 backend가 자연어를 파싱해야 하는데 **교재 금지 사항("Spring Boot LLM 호출 X")에 걸린다.**
- **사람 질문 → agent 추출**, **시스템 자동 생성(SC4) → backend가 채움**으로 나눴다. 시스템 작업은 무엇이 바뀌었는지 backend가 이미 알고 있어 모델이 추측할 이유가 없다.
- 덤으로 `classify_intent` 노드가 할 일이 생겨 평가표 Agent 설계 15점의 **분기 증빙**이 분명해진다.

### 6.3 `compare_options`가 `tool`·`args`를 그대로 돌려준다 (B2)

- 대안마다 실행에 쓸 도구 이름과 인자를 그대로 담는다.
- **근거**: 모델이 대안을 고른 뒤 인자를 **다시 만들면** 숫자가 틀어질 수 있다. 이 프로젝트의 주제가 "잔실수 줄이기"라 그게 가장 치명적이다. 계산이 만든 인자를 그대로 승인 카드에 올리고 그대로 실행하면 사람이 승인한 값과 실행된 값이 반드시 같다.
- `verify` 통과 기준은 "대상 결품 해소 + 새 결품 없음", 최대 2회 재시도. 아키텍처 5장 verify 노드와 4.5 거절 횟수를 그대로 따랐다.

### 6.4 도구를 1차 8개 / 2차 5개로 나눔 (C1)

- **근거**: 평가표 MCP 20점은 "조회·변경 도구와 **설명**을 갖추고 오류·예외 처리가 동작"을 본다. 개수보다 **docstring의 단위 표기와 ToolError의 재시도 정보**가 점수다. 13개를 얕게 만드는 것보다 8개를 제대로 만들고 늘리는 쪽이 낫다.
- 1차 8개는 **SC1~SC4 데모가 끝까지 도는 최소 집합**으로 골랐다. 2차 5개는 조회 폭을 넓히는 것이라 데모를 막지 않는다.

### 6.5 통합 발주(A4)는 MVP에서 뺀다

- **근거**: 도구·계산·승인이 한 벌 더 필요한데 **평가표에 해당 항목이 없다.** 같은 노력을 MCP 오류 처리나 Harness에 쓰는 편이 점수에 직접 닿는다.
- 대신 `compare_options`의 대안 타입에 "다른 제품 몫 재할당(REALLOCATE)"이 이미 있어, 공용 부품을 돌려쓰는 그림은 유지된다.
- 장표에는 향후 과제로 적는다.

### 6.6 자동 분석(B1)은 넣는다

- **근거**: backend가 입고일 변경 후 `trigger = SYSTEM` 작업을 하나 만들면 끝이라 비용이 거의 없는데, 얻는 게 셋이다. ① SC4 시연이 완성된다 ② 작업이 쌓이는 그림이 자연스러워져 **대기열 가산점(+10)** 과 이어진다 ③ 구매·생산관리 두 역할이 같은 결과를 받는 장면이 생긴다.

### 6.7 Harness 한도는 교재 권장값 그대로 (D3)

- 8턴 · 120초 · 같은 도구 3회 · 429·503 2회 재시도.
- **근거**: 교재가 "바꾸면 Harness 명세에 기록하라"고 한다. **바꿀 이유가 아직 없다.** 뼈대에서 도구 2개로 2턴에 끝났고, 도구가 늘어도 8턴 안에 들어온다. 값을 건드리면 설명할 거리만 늘어난다. BOM이 깊어 한도에 걸리면 그때 이유와 함께 올린다.

### 6.8 DB 계정을 스키마별로 나눈다

- `app` / `agent` / `rag` 세 계정, 각자 자기 스키마만.
- **근거**: 아키텍처 11장 보안성 증빙에 "DB 계정 분리"가 들어 있고, 평가표 인증 10점과 닿는다. `init.sql` 몇 줄이면 된다. 한 계정으로 쓰다가 나중에 나누려면 연결 설정을 세 서비스에서 동시에 고쳐야 한다.
- `agent` 계정에만 `CREATE`를 준다. LangGraph checkpointer가 테이블을 직접 만들기 때문이다.

- **구현 메모** (10/20 오후): pgvector 확장을 `public`이 아니라 **`rag` 스키마**에 설치했다. `public`에 두면 `rag` 계정에 `public` 사용 권한을 열어야 해서 "자기 스키마만"이 깨진다. 비밀번호는 `init.sql`에 개발값으로 고정했다 — DB 포트를 밖으로 열지 않으므로 `.env`로 빼는 수고(init.sh 래퍼)보다 단순함이 낫다고 봤다. 외부 배포를 하면 바꾼다.

### 6.9 근거 문서는 3종 (C3)

- 구매 규정 / 협력사 계약 조건 / ECN 3~5건.
- 통합 발주를 뺐으므로 "통합 발주 기준" 문서도 뺐다.
- **협력사 계약 조건을 남긴 이유**: 분할 배송 수수료(1.3·3.4)와 납기 변경 패널티가 여기 들어가고, `compare_options`의 `added_cost`가 그 숫자를 인용한다. 근거 문서가 계산과 이어지는 유일한 문서라 빼면 RAG가 장식이 된다.

### 6.10 `/internal` 1차 8개를 고정 응답으로 먼저 낸다 (B 파트, 10/20 오후)

- **무엇**: DB·계산보다 먼저 8개 엔드포인트를 [contracts.md 2.1](contracts.md) 모양 그대로, 예시 데이터로 연다. 오류 경로(2.5)는 고정이 아니라 실제 검사로 낸다.
- **근거**: C 파트의 도구 8개가 이 응답 모양에 묶여 있다. 계산까지 끝내고 열면 C가 그동안 도구를 못 붙인다. 모양이 먼저 굳으면 B는 안쪽(DB·계산)만 바꾸면 되고 C는 아무것도 안 고쳐도 된다.
- **오류 경로를 진짜로 낸 이유**: "모델이 `retry_hint`를 읽고 인자를 고쳐 다시 부른다"가 평가표 MCP 20점의 핵심인데, 고정 성공 응답만 있으면 C가 이걸 시험할 방법이 없다.
- **버린 대안**: 계약 문서만 주고 C가 자기 쪽에 mock을 만들게 하기 → mock이 두 벌 생기고, 실제 backend와 어긋나는 걸 마지막에 알게 된다 (walking skeleton을 만든 이유와 같음).
- **HTTP 상태**: 없는 것 404, 상태가 안 맞는 것(닫힌 발주) 409, 승인 없음 403, 나머지 400. 4xx면 충분하다는 계약(2.5)이지만 로그에서 구분이 되게 나눴다. business-mcp는 상태가 아니라 `error` 코드로 분기한다.
- **마스킹 모양**: 금액 키는 남기고 값만 `null`. 키를 지우면 역할마다 응답 모양이 달라진다.

### 6.11 나머지 기술 선택

| 항목 | 결정 | 근거 |
|---|---|---|
| Vector DB | pgvector | 컨테이너 하나로 끝난다. Chroma를 더하면 장애 지점과 compose 복잡도만 는다 |
| 인증 | Spring Security + JWT | 역할을 헤더로 agent까지 넘기기 쉽다 (1.1 경로) |
| Agent 구현 | A안 (직접 StateGraph) | 평가표 Agent 설계 15점이 "Node·분기·반복"을 본다. 설계도와 코드 노드 이름을 1:1로 맞춰 그래프 이미지를 증빙으로 낼 수 있다 |
| LLM | 주 1 + 대체 1 | Harness Recovery가 "대체 모델"을 요구한다. 제공자를 다르게 두면 제공자 장애까지 덮어 증빙이 강해진다. 구체 모델은 키를 가진 사람이 정한다 |
| 대기열 | RabbitMQ, 후순위 | 가산점이라 본 점수를 다 채운 뒤에 붙인다. → 10/20 밤에 붙였다 (6.24) |

### 6.12 `analyze_impact` 실제 계산에서 정한 것 (B 파트, 10/20 오후)

- **whatif 연산 이름 = 변경 도구 이름**: verify가 `compare_options`의 `tool`·`args`를 손대지 않고 다시 계산에 넣을 수 있다. 모델이 인자를 옮겨 적다 틀릴 여지가 없다 (6.3과 같은 이유).
- **whatif는 실행 가능성을 보지 않는다**: "그렇게 하면 어떻게 되나"를 묻는 도구라, 리드타임상 불가능한 안이어도 결과를 보여 준다. 실행 가능성은 변경 API와 `compare_options`의 `feasible`이 본다.
- **과잉은 부품마다 1건(가장 큰 날)**: 매일 판정해서 다 내면 같은 재고가 수십 건으로 보인다. 경고가 많으면 아무도 안 본다는 1.3의 이유와 같다.
- **오류 코드 `INVALID_ARGUMENT`를 더했다**: 날짜 형식이 틀렸거나 모르는 `op`일 때 맞는 코드가 9개 중에 없었다. 처음엔 날짜 형식 오류를 `LEADTIME_INFEASIBLE`로 냈는데, 모델이 "리드타임 문제"로 오해해 엉뚱하게 고칠 수 있다. 🟡 C 파트 확인 필요 — business-mcp는 코드를 그대로 전달하므로 고칠 것은 없다.
- **`evidence_uri`를 응답에서 뺐다**: backend는 근거 문서를 모른다. 고정 응답 때 넣은 값이 계약에 남아 있었다. 🟡 C 파트 확인 필요 — 가짜 모델은 키가 없을 때 기본 문서를 읽도록 이미 짜여 있어 흐름은 그대로다.
- **테스트는 Testcontainers**: 골든셋을 H2 같은 가짜 DB로 돌리면 `db/*.sql`이 그대로 안 돈다. 시연과 같은 이미지·같은 SQL로 계산해야 증빙이 된다. `cd backend && mvn test` (Docker 필요).

### 6.13 평가셋 정답을 파일 하나로 모은다 (B 파트, 10/20 오후)

- **결정**: SC 정답을 [`eval/golden.json`](../eval/golden.json) 하나에 두고, backend 테스트와 C 파트 Harness 평가가 같이 읽는다. 칸마다 주인을 나눴다 (질문·도구는 C, whatif·결과는 B).
- **근거**: 정답이 이미 decisions.md 표와 Java 테스트 두 곳에 있었고, C가 평가셋을 따로 만들면 세 곳이 된다. 기획안 PDF로 만들면 SC3처럼 **오류 없이 어긋난다** — AI가 맞게 답해도 오답 처리된다. 파일을 테스트가 읽으면 seed를 바꾸고 정답을 안 고쳤을 때 바로 깨진다.
- **버린 안**: ① 공지만 하고 각자 만든다 → 사람이 매번 맞춰야 하고, 빠뜨려도 모른다. ② 정답을 Java 테스트 안에만 둔다 → C가 Python에서 못 읽는다.
- **비용**: 테스트 코드에서 정답이 한눈에 안 보인다. 대신 실패하면 문항 ID와 기대값·실제값이 같이 나온다.
- **뒤집을 때**: C가 이미 다른 형식을 쓰고 있으면 그쪽에 맞춘다. 바꿀 곳은 `ImpactAnalysisTest`의 읽는 부분뿐이다.

### 6.14 `compare_options` 실제 계산에서 정한 것 (B 파트, 10/20 오후)

- **대안을 만드는 법**: 발주로 못 푸는 결품(`orderable=false`)의 부품마다, 첫 결품일보다 늦게 들어오는 OPEN 발주로 두 가지를 만든다 — 필요한 만큼만 떼어 첫 결품일에 받기(`split_po`), 발주 전량을 첫 결품일에 받기(`request_due_date_change`). 필요한 만큼 = 그 부품 결품 중 가장 큰 부족량.
- **대안마다 실제로 다시 계산한다**: 원래 가정 + 대안을 whatif로 넣어 `analyze_impact`를 돌리고, 대상 결품이 풀리는지(`resolves`)와 새 결품(`side_effects`)을 채운다. 대안을 규칙으로 짐작하면 SC1의 "11/27분에서 당기기"처럼 그럴듯하지만 연쇄 결품이 남는 안을 걸러내지 못한다 (7.4).
- **`orderable=true` 결품은 대상이 아니다**: 지금 발주하면 제때 오는 결품은 기획안이 "실수가 아니라 정상 안내"라고 한 것이다. 기존 발주를 당길 이유가 없다. 그래서 대안의 `resolves`도 발주로 못 푸는 결품만 본다.
- **리드타임상 불가능한 대안은 아예 안 낸다**: 승인까지 갔다가 변경 API에서 `LEADTIME_INFEASIBLE`로 막히면 사람 시간만 쓴다.
- **당김 비용을 개·일 단위로 바꿨다**: 발주 1건 기준(원/일)이면 500개 전량을 당기는 비용과 100개만 떼어 당기는 비용이 같아서, 분할 수수료만큼 **분할이 항상 비싸진다.** "급한 만큼만 떼어 먼저 받는다"(3.1)는 분할의 목적과 반대다. 값은 단가의 약 5%로 잡아, SC1 승인 카드의 340,000원(3.5)은 그대로다.
- **위험**: 납기 준수율 90% 이상 LOW · 80% 이상 MID · 그 밑 HIGH, **2주 넘게 당기면 한 단계 위.** 많이 당길수록 협력사가 생산 일정을 다시 짜야 해서 못 지킬 가능성이 커진다. 파워링크(78%)는 항상 HIGH다 — SC4에서 이미 지연을 낸 협력사라 맞는 결과다.
- **추천 순서**: 결품을 푸는 것 → 부작용 없는 것 → 위험 낮은 것 → 싼 것. 위험을 비용보다 앞에 둔 이유: 싼 대안이 납기를 못 지키면 결품이 그대로 남아 비용 절감이 의미 없다. 푸는 대안이 없으면 추천하지 않는다(`null`) — 모델이 "그나마 나은 것"을 정답처럼 말하지 않게.
- **추천은 부품마다 하나**: SC2는 릴레이·전원 모듈이 따로 모자라서 대안 하나로 못 푼다. 하나만 추천하면 모델이 절반만 해결하고 끝낸다.
- **발주일 2건을 고쳤다**: 처음 seed의 `PO-2610-113`·`114`(11/27 전원 모듈·릴레이) 발주일이 10/28이라 11/23로 당길 수 없었다. 그러면 기획안 SC2 해결 예시("11/27분을 11/23 전으로")가 불가능해진다. 발주일은 원래 지어 넣은 값이라 10/23으로 당겼다 (7.1).
- **아직 안 만든 것**
  - **새 발주 대안**(추가 발주, 대체 협력사 긴급 구매): 실행할 도구(`create_po`)가 도구 목록에 없다. 승인 카드로 올릴 수 없는 대안을 내면 모델이 고른 뒤 막힌다. 넣으려면 도구를 하나 더 열어야 해서 **팀 결정 사항**이다 (5절 11번). 대체 협력사 평가지표는 seed에 이미 있다.
  - **여러 대안을 함께 적용한 검증**: SC2의 두 추천안은 서로 다른 부품이라 겹치지 않는다. 같은 부품에 대안 둘을 겹쳐 쓰는 경우가 생기면 그때 넣는다.
  - `REALLOCATE`(다른 제품 생산 조정): 생산계획 변경은 PLANNER가 화면에서 하는 일이고 도구가 없다.

### 6.15 ✅ 생산관리 담당자는 추가 비용을 등급으로만 본다 (10/20 저녁)

- **결정**: 대안의 `added_cost` 옆에 `cost_level`(`LOW`·`MID`·`HIGH`)을 붙인다. 생산관리 담당자는 금액이 `null`이고 등급만 보인다. 구매·팀장은 둘 다 보인다.
- **새로 정한 게 아니다**: 기획안 2.4 표에 "해결 방법별 추가 비용 — 생산관리: 낮음/중간/높음만"이 이미 있었다. contracts 1.2로 옮길 때 빠졌던 것을 되살렸다. 그래서 팀 논의 없이 B가 반영했다.
- **왜 등급이라도 보여 주나**: 생산관리 담당자가 "일정을 다시 잡을지, 구매에 대안을 맡길지"를 판단하려면 대안이 비싼지 싼지는 알아야 한다. 정확한 금액은 협력사 계약 정보라 구매 쪽만 본다.
- **기준**: 30만 원 미만 LOW · 100만 원 미만 MID · 그 이상 HIGH. seed의 대안 비용이 9만~170만 원이라 세 등급이 고르게 나오는 선으로 잡았다 (SC4 분할 23만 = LOW, SC1 분할 39만 = MID, SC1 전량 170만 = HIGH). 바꾸려면 `OptionAnalysis.COST_*`과 contracts 1.2 표를 같이 고친다.
- **`risk`와 다른 것**: `risk`는 협력사가 날짜를 못 지킬 가능성, `cost_level`은 돈의 크기다. 이름이 비슷한 "낮음/중간/높음"이라 헷갈리지 않게 칸을 나눴다.

### 6.16 🟡 새 발주는 도구로 열지 않는다 (10/20 저녁, B 제안)

- **결정**: 추가 발주·대체 협력사 긴급 구매를 실행하는 도구(`create_po`)를 만들지 않는다. `compare_options`는 기존 발주를 당기는 대안만 낸다.
- **근거**
  - 시연 시나리오가 이것 없이 성립한다. SC1·SC2·SC4는 기존 발주를 당겨서 풀리고, SC2·SC3의 남은 결품은 `orderable=true`라 "지금 발주하면 제때 온다"는 **정상 안내**다. 기획안도 추가 발주를 "실수가 아니라 정상 안내"로 분류했다 (기획안 1.3).
  - 열면 세 파트 일이 같이 는다: C는 도구와 승인 종류 추가, A는 승인 카드에 "새 발주" 모양 추가, B는 생성 API와 MOQ·리드타임 검사. 평가표에 이 기능을 따로 보는 항목이 없다.
  - "통합 발주는 MVP에서 뺀다"(6.5)와 같은 방향이다.
- **버린 안**: 도구 없이 대안 목록에만 보여 주기 → 모델이 그 대안을 고르면 승인 카드로 올릴 수 없어 흐름이 막힌다. 보여 줄 거면 실행까지 되어야 한다.
- **뒤집을 때**: 팀이 "대체 협력사 긴급 구매"를 시연하고 싶다면 연다. 대체 협력사 데이터는 seed에 이미 있다(누리전자·코어칩스). 바꿀 곳: `OptionAnalysis`에 대안 종류 추가, `/internal/purchase-orders` POST, contracts 2.1·2.3, business-mcp 도구 1개.
- **상태**: B 제안으로 진행 중. 팀에서 이견이 나오면 위 순서로 뒤집는다.

### 6.17 인증·마스킹 구현에서 정한 것 (B 파트, 10/20 저녁)

- **JWT는 Spring Security 안의 것만 쓴다** (`oauth2-resource-server`의 Nimbus). jjwt 같은 라이브러리를 더하지 않는다. 서명은 HS256 — 발급과 검증이 둘 다 backend라 공개키 방식으로 나눌 이유가 없다.
- **토큰 8시간, 갱신 토큰 없음**: 시연 하루면 충분하다. 갱신 흐름은 화면과 backend 양쪽 일이 생긴다.
- **SSE만 `?access_token=`**: 브라우저 `EventSource`는 헤더를 못 붙인다. 주소에 실은 토큰은 서버 로그에 남을 수 있어서 `/stream` 경로에서만 받는다. 버린 안: SSE를 `fetch` 스트림으로 바꾸기 → 화면 쪽 재연결 처리를 직접 짜야 한다.
- **SSE 비동기 재진입은 검사하지 않는다**: Spring Security 6은 SSE의 비동기 응답 재진입까지 다시 검사하는데, 그때 거부되면 이미 보낸 응답 위에서 오류가 나 스트림이 깨진다. 첫 요청에서 검사했으므로 재진입(`ASYNC`)은 통과시킨다.
- **마스킹은 응답 직전에 칸 이름으로 한다** (`ResponseBodyAdvice`). API마다 가리면 새 API에서 빠뜨린다.
- **`X-Role`이 없으면 다 가린다(PLANNER 기준)**: fail-closed. 반대(없으면 다 보여 줌)로 하면, C 파트가 헤더를 빠뜨린 동안 생산관리 담당자 질문에 단가가 그대로 나간다. 지금 agent는 아직 헤더를 안 넘기므로 AI 답변에 금액이 안 나온다 — 이게 C 파트가 헤더를 붙이면 풀린다.
- **`/internal/**`는 아직 열려 있다**: 서비스 토큰(`X-Service-Token`)은 9단계다. JWT로 막지 않는 이유: 사람이 아니라 서비스가 부르는 곳이라 사용자 토큰이 없다.
- **질문한 사람만 SSE를 볼 수 있다**: 다른 사람이면 403. 팀장은 승인 대기함(7단계)으로 카드를 받는다.
- **화면에 임시 로그인 버튼을 B가 넣었다**: `/api/**`가 로그인 필수가 되는 순간 기존 화면의 질문 버튼이 401로 막혀서, 흐름을 유지하려고 최소한으로 넣었다(`frontend/index.html`의 계정 버튼 3개). 실제 로그인 화면은 A 파트가 만든다.

### 6.18 승인·변경 구현에서 정한 것 (B 파트, 10/20 밤)

- **실행 조건은 "승인과 정확히 같은 호출"**: 승인이 `APPROVED`이고 도구 이름과 인자가 카드와 하나도 다르지 않아야 한다. 인자 하나만 바꿔도(100개 → 200개) 거부한다. 모델이 승인 뒤에 인자를 고쳐 부르는 길을 막는 것이 승인의 목적이다 (아키텍처 10장). 숫자 `100`과 문자열 `"100"`은 같다고 본다 — JSON을 거치며 타입이 바뀔 수 있다.
- **승인 행을 잠그고(`for update`) 실행 후 `EXECUTED`로 바꾼다**: 같은 승인으로 두 번 실행되지 않는다. 변경·이력·승인 상태를 한 트랜잭션에 묶어, 이력 없는 변경이나 실행 안 된 `EXECUTED`가 생기지 않는다 (AUD-001).
- **같은 이벤트가 다시 오면 같은 카드**: `agent-draft`는 이벤트 전송이 실패하면 3번까지 다시 보낸다. 같은 작업·도구·인자의 PENDING 카드가 있으면 그걸 돌려주고 화면에도 다시 보내지 않는다. 버린 안: agent가 이벤트 ID를 붙여 보내게 하기 → C 파트 일이 늘고, 도구·인자가 같으면 같은 카드라는 기준이 더 단순하다.
- **팀장 결정과 agent 재개를 묶지 않는다**: 결정을 먼저 저장하고 재개는 뒤에서 요청한다. agent가 죽어 있어도 사람의 결정은 남아야 한다. 재개가 실패하면 질문자 화면에 `FAILED`가 간다.
- **화면 변경 2개는 승인 없이 바로 바꾸고 이력만 남긴다**: 생산 일정 변경은 생산관리팀의 결정이고, 협력사 지연은 우리가 정하는 게 아니라 **통보받은 사실**이다. 발주 변경처럼 회사 밖으로 나가는 약속이 아니다. 협력사 지연은 리드타임 검사도 하지 않는다 — 날짜를 정한 쪽이 협력사다. 대신 사유를 필수로 받는다.
- **생산계획 변경은 PLANNER만**: 팀장이 가진 상위 권한은 **구매** 권한이다 (1.4). 생산 일정은 다른 팀의 일이다.
- **분할로 생긴 새 발주는 원 발주의 협력사·단가·발주일을 물려받는다**: 같은 물량을 나눠 받는 것이지 새로 주문한 게 아니다 (3.4와 같은 이유). 발주일을 물려받아야 리드타임 검사(7.2)도 원 발주 기준으로 이어진다.
- **화면 변경 API의 요청 모양은 프론트 브랜치를 따랐다** (`{date, qty}`, `{due_date, reason}`): 프론트가 먼저 정해 두었고, backend 쪽에 다르게 할 이유가 없었다. 반대로 로그인 요청(`user_id`)과 조회 응답 모양은 backend 쪽을 유지했다 — 조회 응답은 AI 도구(`/internal`)와 같은 모양이어야 화면과 AI가 같은 숫자를 본다. 프론트는 `services/api.ts` 한 곳에서 변환하도록 이미 짜여 있다.
- **프론트 브랜치를 main에 합쳤다** (사용자 지시): `frontend/index.html` 충돌은 프론트 것을 썼다. 6단계에서 흐름 유지용으로 넣었던 임시 로그인 버튼은 사라졌다.
- **프론트에만 있는 업무는 backend에 넣지 않았다**: 입고 검수 수량(`received`·`passed`·`failed`), 해결안 등급(A~D)·우선순위·검수 상태. 계약에 없고, 넣으면 테이블과 API가 늘어난다. 시연에 필요한지는 팀이 정한다 (5절 14번).

### 6.19 AI 팀원의 통합 브랜치를 기준으로 합쳤다 (B 파트, 10/20 밤)

- **무슨 일**: B가 프론트 API 연결(로그인 `user_id`, 조회 응답 변환, 승인함 실제 API, compose API 모드)을 하는 동안, AI 팀원도 `integration-draft`에서 같은 일을 해 두었다. 같은 파일(`frontend/src/services/api.ts`)을 양쪽에서 고치면 병합 때 충돌이 난다.
- **결정**: **AI 팀원 쪽을 기준으로 삼았다.** B의 미커밋 프론트 변경은 버리고, 로컬 main을 `integration-draft`로 당긴 뒤(B의 마지막 커밋에서 갈라져 있어 그대로 앞으로 이어짐) 그 위에 B만 가진 것을 얹었다.
  - backend: 재고·발주 응답에 협력사 이름·리드타임·사용 제품(`used_in`) 칸 추가 — 팀원 변환 코드가 빈 값으로 두던 칸을 채운다
  - 프론트: 팀원 변환 함수(`toWorkspace`·`toApprovals`)에 위 칸과 요청자 이름을 연결, 변환 테스트(`tests/api.test.ts`), 자재 화면의 완제품 이름을 서버 데이터에서 가져오기
- **근거**: 이미 agent와 같이 돌려 본 쪽이 팀원 브랜치다. B 쪽을 기준으로 하면 팀원이 자기 변경을 다시 맞춰야 한다. B만 가진 것은 칸 추가라 얹기 쉽다.
- **compose의 화면 모드 변수 이름**은 팀원 것(`VITE_DATA_MODE`, 기본 `api`)을 그대로 쓴다.
- **병합 전 점검에서 고친 것**: business-mcp(httpx)는 비어 있는 인자를 `?item_id=`처럼 빈 값으로 보낸다. backend가 이걸 값으로 받아서 `get_inventory`는 **오류 없이 빈 목록**을, `list_receipts`는 `NOT_FOUND`를 냈다. 모델이 "재고 없음"으로 읽을 수 있는 조용한 오류라, 부르는 쪽이 아니라 **받는 쪽(backend)에서 빈 값을 "조건 없음"으로** 보게 고쳤다 (`InternalApi.blankToNull`, 회귀 테스트 있음).
- **병합 전 확인한 흐름** (가짜 모델, 새 DB): 생산관리 질문 → 영향 분석 / 생산관리의 해결 요청 → 승인 없이 안내 / 구매 요청 → 승인 요청 → 팀장 거절(사유 필수) → AI가 다른 대안 → 승인 → 실행 / 화면의 협력사 지연 입력·일정 변경 권한 / 역할별 금액 가리기. AI 쪽 `eval_golden.py`도 공유 평가셋으로 전부 통과.

### 6.20 작업·이벤트를 DB로 옮겼다 (B 파트, 10/20 밤, 8단계)

- **무엇**: `ai_task`(작업 한 건, 상태·답변·결과)와 `task_event`(SSE로 보낸 이벤트 그대로)를 DB에 둔다. 지금 열려 있는 SSE 연결만 메모리에 둔다.
- **근거**: 승인은 사람이 하는 일이라 몇 분~몇 시간 걸린다. 그 사이 backend가 재시작되면 메모리의 작업이 사라져 agent가 재개하며 보낸 이벤트가 404가 되고, 화면은 결과를 다시 그릴 수 없었다. 승인 카드(이미 DB)와 agent checkpointer(이미 DB)만 남고 작업만 사라지는 셈이었다. 실제로 승인 대기 중 backend를 재시작한 뒤 승인 → 재개 → 실행까지 이어지는 것을 확인했다.
- **이벤트는 보낸 모양 그대로 jsonb로**: 종류마다 칸이 달라(TOOL_END의 `ms`, APPROVAL_REQUIRED의 `args` …) 칸을 나누면 이벤트 종류가 늘 때마다 테이블을 고쳐야 한다. 다시 보낼 때는 그대로 꺼내 보내면 된다. 자주 찾는 것(상태·답변)만 `ai_task`에 칸으로 둔다.
- **상태는 이벤트에서 정한다**: TOOL_* → RUNNING, APPROVAL_REQUIRED → WAITING_APPROVAL, 팀장 결정 → RUNNING, DONE/FAILED → 끝. agent가 상태를 따로 알려 주지 않아도 된다. 끝난 작업에 늦게 온 이벤트는 쌓이지만 상태는 다시 바뀌지 않는다.
- **seq는 작업별 자물쇠 안에서 `max+1`**: backend가 한 대라 충분하다. 여러 대로 늘리면 DB 시퀀스나 행 잠금으로 바꾼다 (코드에 `ponytail:` 표시).
- **작업 목록 권한**: 기획안 2.3 "작업 기록 보기 — 생산관리 내 것만, 구매·팀장 전체"를 그대로. 생산관리가 전체를 달라고 해도 403 대신 자기 것만 준다 — 화면이 역할마다 다른 주소를 부르지 않아도 된다. SSE 구독은 지금처럼 질문한 사람만.
- **작업 코드를 `Tasks.java`로 옮겼다**: `BackendApplication`은 시작점과 모듈 목록만 남았다 (아키텍처 3.1 task 모듈).
- **승인 카드가 작업을 참조한다** (`approval.task_id → ai_task`): 작업이 메모리에 있을 때는 FK를 못 걸었다.

### 6.21 9단계에서 정한 것 — 서비스 토큰·자동 분석·2차 도구·과잉 대안·평가지표 입력 (B 파트, 10/20 밤)

- **서비스 토큰은 서비스마다, 경로마다**: agent 토큰은 진행 이벤트(`/internal/tasks/**`)만, business-mcp 토큰은 업무 API만 연다. 하나로 다 열면 agent가 MCP를 건너뛰고 업무 API를 직접 부를 수 있다 — 교재 5장 경로(agent → MCP → backend)를 권한으로 강제한다. business-mcp는 agent 헤더를 그대로 넘기는데(contracts 1.1), **토큰만은 자기 것으로 바꿔** 보낸다. 비교는 시간이 일정한 방식(`MessageDigest.isEqual`).
- **자동 분석은 PLANNER 역할로 돌린다**: 협력사 지연 결과는 구매와 생산관리가 같이 봐야 한다(아키텍처 4.6). 한 작업을 두 역할이 보므로 금액을 가장 많이 가린 쪽으로 만들어야 생산관리에게 금액이 새지 않는다. 작업 주인은 지연을 입력한 구매 담당자, 생산관리 작업 목록에도 나온다. 버린 안: 역할마다 작업을 하나씩 만들기 → 같은 분석을 두 번 돌리고 이력이 두 줄이 된다.
- **자동 분석의 whatif는 backend가 채운다** (contracts 2.6): 무엇이 바뀌었는지 backend가 이미 안다. 변경은 이미 DB에 들어갔으므로 같은 날짜로 한 번 더 적용해도 결과가 같다.
- **과잉 대안을 넣었다**: 2차 변경 도구(수량 변경·취소)가 생겨 기획안의 SC2·SC3 해결 예시("플러그 케이스 800→500", "옛 케이스 취소", "전지 입고 미루기")를 대안으로 낼 수 있게 됐다. 계산으로 나온 추천이 기획안 예시와 같다. 코인전지 취소처럼 다른 생산을 모자라게 하는 안은 다시 계산해 걸러진다.
- **과잉 대안의 비용은 0, 대신 `saved_amount`**: 취소·감량 수수료는 계약 조건 문서에 있고 평가지표에는 칸이 없다. 근거 없는 숫자를 지어내지 않는다. 필요하면 `supplier_metric`에 `cancel_fee` 칸을 더한다.
- **수량 변경은 MOQ를 본다, 분할은 안 본다 (3.4)**: 분할은 같은 물량을 나눠 받는 것이고, 수량 변경은 주문량 자체가 줄어든다 — 협력사 생산 로트 기준이 그대로 적용된다.
- **평가지표 입력은 화면 API에만**: 2.4 결정 그대로. 보낸 칸만 바꾸고 범위를 검사한다. 칸 이름은 코드의 허용 목록에서만 SQL에 들어간다.
- **business-mcp에 도구 5개를 B가 등록했다**: 사용자 지시("다 진행"). agent 그래프는 건드리지 않았고 진행 표시 문구(LABELS)만 더했다. 언제 어떤 도구를 쓸지는 C가 정한다 — 특히 과잉 대안(`target_rule = INV-003`)을 승인 흐름에 태우는 것.
- **평가는 새 DB에서**: 승인·실행 테스트를 하면 DB의 발주가 실제로 바뀐다. 그 상태로 `eval_golden.py`를 돌리면 SC1 해결안 검증이 "이미 풀린 결품" 때문에 실패한다. 평가 전에 `docker compose down -v`.

### 6.22 `side_effects` 계산 명세를 반영했다 (B 파트, 10/20 밤)

- **출처**: 팀 내 `BOM_compare_options-side_effects계산명세.md` (저장소 밖). 5단계 전에 쓰인 문서라 "side_effects는 고정 `[]`"라고 적혀 있었지만, 5단계에서 이미 계산하고 있었다. 빠져 있던 것은 세 가지였다.
- **WORSENED 추가**: 전에는 "전에 없던 (부품, 계획, 날짜)"만 부작용으로 봤다. 원래 있던 결품이 더 커지는 경우를 놓쳤다. 이제 결품량을 비교해 늘어나면 잡는다. 시나리오 데이터에선 생기지 않아 일부러 만든 사례로 테스트한다 (SC3 + 1/22 코인전지 감량 → 11/15분 취소 시 1/25 결품 300 → 1,100).
- **원소 형식**: 명세대로 `type`·`rule_id`·`product_id`·전후 결품량·증가량. AI가 "어느 제품이 얼마나 더 모자라지는지"를 지어내지 않고 그대로 말할 수 있다.
- **`remaining_issues` 추가, `resolves`는 유지**: 남은 결품은 부작용이 아니라 "덜 풀렸다"는 뜻이라 칸을 나눴다 (명세 4절). `resolves`를 지우면 이미 이 칸을 읽는 agent verify가 깨져서 둘 다 둔다.
- **같은 부품의 다른 계획도 부작용으로 본다**: 전에는 결품 대안에서 대상 부품의 결품을 통째로 부작용에서 뺐다. 이제 "풀려던 결품(대상 키)"만 빼고, 같은 부품이라도 다른 계획에 새로 생기거나 커지면 부작용이다 (명세 2절 "그 부품을 사용하는 모든 계획").
- **요청 칸 이름**: 명세는 `base_whatif_ops`를 제안했지만 이미 `whatif`로 확정·구현돼 있어(contracts 2.3) 그대로 둔다.
- 평가셋 SC1~SC4의 대안마다 `side_effects`·`remaining_issues` 정답을 넣었다. 추천 결과는 바뀌지 않았다.

### 6.23 프론트 API 모드의 빈 화면을 채웠다 (B 파트, 10/20 밤, 사용자 지시)

- **무엇이 비어 있었나**: 업무 현황의 "신규 위험"이 항상 0, 해결안 비교는 "API 미연결", 생산계획 "영향 미리보기"는 "API 계약 필요". 셋 다 backend에 계산은 있는데 화면이 부를 길이 없었다(`/internal`은 서비스 토큰 전용).
- **화면용 분석 API를 열었다**: `POST /api/analysis/impact`·`/api/analysis/options`. **AI 도구와 같은 메서드**를 부른다 — 화면과 AI가 같은 숫자를 봐야 한다(아키텍처 1.1). 금액은 JWT 역할대로 가려진다.
- **업무 현황·해결안 비교는 지금 DB 상태를 본다** (whatif 없음): 생산관리가 일정을 저장하거나 구매가 지연을 입력하면 다시 불러와 바로 위험·해결안이 바뀐다. 미리보기만 whatif를 넣는다 (저장 전이라 DB는 그대로).
- **API 모드에는 사람의 검수·우선순위 단계가 없다**: 등급(`cost_level`)과 추천은 시스템 계산값이라 "시스템 계산"으로 보여 주고, 추천안이 1순위다. 목데이터 모드의 "구매 검수 → 등급 확정 → 생산관리 우선순위" 화면은 그대로 둔다 (5절 14번 팀 결정 대기).
- **"승인 요청" 버튼은 AI 작업을 만든다**: 화면이 승인 카드를 직접 만들지 않는다 — 카드는 AI가 검증(verify)을 거쳐 올린다(contracts 3.3). 버튼은 "지금 계획 기준으로 부족한 {부품} 해결 방법 만들어 줘" 작업을 만들고, AI는 같은 계산의 추천안으로 승인을 올린다.
  - **질문에 해결안 문장을 넣지 않는다**: 처음엔 "PO-…에서 100개를 11/25에 먼저 받는다 — 이걸로 승인 요청"으로 물었더니, AI가 그 문장을 **가정 변경으로 읽어** 이미 풀린 상태로 분석하고 "조치할 결품 없음"으로 끝났다.
  - 한계: 과잉 해결안(감량·취소)은 agent가 아직 승인 흐름에 태우지 않아 버튼을 눌러도 승인까지 가지 않는다 (C 파트, 계약 표 23번).
- **표시 문구**: API 모드에서 데모 환경 이름("정상 운영"), "데모 분석 결과", "검수 v1", "생산관리 결정 대기"가 나오던 것을 실제 상태에 맞게 바꿨다.
- 확인: 화면이 부르는 순서 그대로 일정 변경 → 위험 2건 → 해결안(생산관리는 등급만, 구매는 금액) → 승인 요청 → 팀장 승인 → 실행 → 위험 0건. 브라우저에서 미리보기·해결안 비교·업무 현황을 직접 봤다.

### 6.24 AI 작업 대기열(RabbitMQ)을 붙였다 — 꺼내는 쪽도 backend (B 파트, 10/20 밤, 사용자 지시)

- **무엇**: 작업 접수(`/agent/tasks`)와 승인 후 재개(`/resume`) 요청을 agent에 바로 보내지 않고 `ai.tasks` 대기열에 넣는다. backend의 소비자(`Tasks.deliver`)가 꺼내 지금처럼 HTTP로 보낸다. 실패하면 30초 뒤, 또 실패하면 2분 뒤 다시 보내고, 3번째도 실패하면 `ai.tasks.dlq`에 마지막 오류와 함께 남기고 `FAILED`. 설계는 아키텍처 7.1 그대로다. 코드: `TaskQueue.java`(대기열 설정), `Tasks.java`(넣기·꺼내기).
- **왜 backend가 꺼내나**: 아키텍처 7.1은 agent가 소비자다. 그러면 agent(C 파트) 코드가 HTTP 대신 대기열을 읽게 바뀌어야 하고, C의 남은 일(RAG·과잉 대안)과 겹친다. backend가 꺼내도 "작업이 사라지지 않는다 · 시간을 두고 다시 보낸다 · 끝내 실패하면 DLQ"는 똑같이 된다. agent는 한 줄도 안 바뀌었다.
  - **포기한 것**: 몰린 작업을 하나씩 **실행**하지는 못한다. agent는 요청을 받자마자 202를 주고 뒤에서 돌리므로, 대기열이 순서대로 넘겨도 실행은 동시에 일어난다. 실행 순서까지 막으려면 agent가 소비자가 되어 작업이 끝난 뒤 ack해야 한다 (버린 안 = 아키텍처 7.1 원안). 필요해지면 그때 C와 같이 바꾼다 — backend는 `deliver`만 지우면 된다.
- **이전과 달라진 것**: 전에는 agent가 꺼져 있으면 바로 `FAILED`였다. 이제는 2분 30초 동안 기다리며 다시 보낸다. agent를 껐다 켜는 장애 시연(아키텍처 11장 "신뢰성")에서 작업이 이어진다 — 실제로 agent를 끈 채 질문하고 30초 안에 켜서 `DONE`까지 가는 것을 확인했다.
- **재시도 대기 방법 = 메시지 수명(TTL) + dead-letter**: 재시도 대기열엔 소비자가 없고, 수명이 다한 메시지를 RabbitMQ가 `ai.tasks`로 되돌린다. 지연 플러그인을 깔지 않아도 된다. 버린 안: 소비자 안에서 `sleep` 후 재시도 → 기다리는 동안 뒤의 작업이 전부 막히고, backend가 재시작하면 기다리던 작업이 사라진다.
- **중복 방지는 backend가 작업 상태로**: backend가 처리 도중 죽으면 RabbitMQ가 같은 메시지를 다시 준다. 접수는 작업이 아직 `QUEUED`일 때만, 재개는 작업이 끝나지 않았을 때만 보낸다. 아키텍처 7.1은 agent가 `taskId`로 거르게 했지만, 상태를 아는 쪽이 backend라 여기서 거르면 agent를 안 고쳐도 된다.
- **agent 호출에 3초 제한**: 전에는 제한이 없었다. 소비자가 하나라서 agent가 응답 없이 멈추면 뒤의 작업이 전부 밀린다. 3초는 아키텍처 4.2 표 값.
- **RabbitMQ에 넣는 것 자체가 실패하면** 바로 `FAILED`(`QUEUE_UNAVAILABLE`). 작업 행은 이미 저장돼 있어서, 안 남기면 화면이 영원히 기다린다.
- **compose**: `rabbitmq:4.1`, 포트 공개 안 함, 볼륨(`mqdata`)으로 재시작해도 대기 중 작업이 남는다. guest 계정은 컨테이너 밖에서 못 붙어 `bom` 계정을 둔다. 확인: `docker compose exec rabbitmq rabbitmqctl list_queues name messages`.
- **안 한 것**: 작업 목록의 "재시도" 버튼(아키텍처 7.1) — 화면(A)과 API가 같이 필요하다. 지금은 같은 질문을 다시 하면 된다. 재시도 중이라는 진행 이벤트도 내지 않는다 — 새 이벤트 종류는 화면 계약(3.2)이 바뀐다.

### 6.25 ✅ 해결안 비교 화면은 구매팀장만 본다 (10/21, 팀 토의 결과, 사용자 지시)

- **무엇**: 화면의 "해결안 비교" 탭을 APPROVER에게만 보인다. 생산관리·구매 담당자에게는 메뉴, 주소 직접 이동(`/solutions` → 업무 현황), 다른 화면 안의 "해결안 비교" 링크, 업무 현황의 할 일 카드(우선순위 결정·비용등급 검수·승인 요청)가 모두 없다.
- **근거**: 팀 토의에서 "팀장 말고는 볼 필요 없다"로 정했다. 여러 대안을 견주어 고르는 일은 승인하는 사람의 일이고, 생산관리·구매는 AI 답변과 업무 현황으로 충분하다는 판단.
- **알고 정한 비용**: 구매 담당자의 화면 "승인 요청" 버튼이 이 화면에만 있었다. 이제 구매 담당자는 **AI 채팅으로 승인을 요청**한다 ("지금 생산계획 기준으로 부족한 MCU 해결 방법 만들어 줘"). 버린 안: 생산관리만 숨기고 구매는 남기기 — 사용자가 요청대로 팀장만으로 정했다.
- **목데이터 모드 영향**: 프론트 목데이터 모드의 "구매 검수 → 등급 확정 → 생산관리 우선순위" 단계는 이 화면에 있어 생산관리·구매가 더는 할 수 없다. 이 흐름을 backend에 둘지는 5절 14번(팀 결정 대기)인데, 이번 결정으로 사실상 쓰지 않는 쪽에 가까워졌다.
- **어디까지 막나**: 화면에서 숨긴 것이다. 같은 계산을 내는 `POST /api/analysis/options`는 역할 검사 없이 그대로 열려 있다 — 업무 현황 위험 표시와 AI가 같은 계산을 쓴다. API까지 막으려면 별도로 정한다.
- **코드**: `frontend/src/stores/workspace.ts`의 `approver`, `main.ts` 라우터 검사, `App.vue` 메뉴·역할 변경 시 이동, 링크가 있던 화면 5곳. 프론트(A) 코드지만 사용자 지시로 B가 최소로 고쳤다.

### 6.26 새로고침해도 로그인을 잇는다 — sessionStorage (10/21, 사용자 지시)

- **무엇**: 로그인 정보(토큰·역할·이름)를 브라우저 **탭 저장소(sessionStorage)**에 둔다. 새로고침하면 그대로 이어지고, 탭을 닫거나 로그아웃하면 지워진다. 전에는 메모리에만 있어 새로고침마다 로그아웃됐다. 코드: `frontend/src/stores/workspace.ts`의 `remember()`와 시작할 때 복원.
- **만료**: 토큰은 8시간(6.17). 만료되거나 잘못된 토큰이면 첫 요청이 401 → `session-expired` → 로그인 화면, 저장값도 지운다. 브라우저에서 토큰을 일부러 망가뜨려 확인했다.
- **버린 안**
  - localStorage: 브라우저를 껐다 켜도 남아서, 시연 PC에서 다른 사람이 앞사람 계정으로 들어가 있게 된다. 탭마다 다른 역할로 로그인해 비교하는 시연도 못 한다 (localStorage는 탭끼리 공유).
  - 갱신 토큰·HttpOnly 쿠키: 가장 안전하지만 backend 로그인·SSE 인증을 바꿔야 한다. 시연 범위에선 과하다.
- **저장 형식이 바뀌어도 이어지게** (10/21 추가): C의 다건 승인 병합으로 로그인 정보에 `userId`가 생겼는데, 그 전에 저장된 로그인은 이 칸이 없어 채팅창이 **내가 방금 한 질문을 남의 작업으로 보고 읽기 전용으로 열었다**(카드·메모 칸이 안 보임). 복원할 때 `userId`가 없으면 토큰(JWT의 `sub`)에서 채운다.
- **비용**: 저장소의 토큰은 페이지 스크립트가 읽을 수 있다 (XSS가 생기면 노출). 메모리에 둘 때도 같은 스크립트가 읽을 수 있어 차이는 "새로고침 뒤에도 남는다" 정도다. 밖에 공개할 때는 쿠키 방식으로 바꾼다.

### 6.27 답변 가독성 — 목록은 코드가, 모델은 결론만 (10/21, 사용자 지시)

- **무엇이 문제였나** (실제 gpt-4o-mini, SC2 질문): 별표(`**`)가 글자 그대로 보였다. 결품 6건 중 3~5건만 옮겼고, "새 발주로는 늦음"을 "주문할 수 없다"로 바꿔 썼다. 부품 ID를 마음대로 번역했고("케이스 스위치"), 연쇄 결품을 엉뚱한 생산에 붙였으며, 근거는 JSON 그대로 나왔다.
- **결정**
  1. **목록은 코드가 쓴다.** 영향 분석 답변의 결품·주의·과잉 목록은 `describe_impact`가 계산 결과에서 그대로 만들고, 모델은 결론 1~2문장만 쓴다(숫자 없이). 프롬프트로 "빠짐없이"를 세 번 바꿔 가며 시켜도 한두 건씩 빠지거나 숫자가 틀렸다. 숫자는 계산한 쪽이 옮겨야 틀리지 않는다 (교재 Harness "모델에게 계산을 맡기지 않는다"와 같은 이유).
  2. **연쇄 결품도 코드가 판정한다** (`chain_note`): 질문에서 바꾸지 않은 계획에 생긴 결품. 계산으로 정확히 나온다. 발주 지연 질문처럼 바꾼 계획이 없으면 쓰지 않는다.
  3. **모델 글은 첫 문단만 남긴다** (`lead_text`): 지시를 어기고 목록이나 마크다운 표를 붙인 적이 있다. 거기서 자른다.
  4. **이름 칸**: backend `analyze_impact` 항목에 `item_name`·`product_name`. ID 번역을 막는 근본 해결이고, 화면 영향 결과에도 이름이 나온다.
  5. **평문 + 모양 약속**: 프롬프트에 마크다운 금지. 답변은 "결론 → 빈 줄 → '제목 n건:' + '- 항목'" 모양이고, 화면(`services/answer.ts`)이 이걸 결론·제목·목록으로 그린다. 남은 `**`·`#`·백틱은 화면이 지운다. HTML로 넣지 않아 답변 안의 태그도 글자로만 보인다.
  6. **근거는 문서 카드로**: 제목, 조항·버전·시행일, 원문 발췌, `doc://` 주소. 같은 조항은 한 번만. 답변 끝 목록에서는 주소를 빼 짧게 했다.
  7. **색은 뜻으로만**: 빨강 = 손써야 함(결품, 새 발주로는 늦음), 노랑 = 지켜볼 것(주의·과잉, 연쇄 결품 상자), 초록 = 괜찮음(지금 발주하면 제때, 실행한 변경). 기존 badge 색을 그대로 써서 화면 전체와 같다. 항목은 "어디(작게) → 무엇(굵게) → 상태 꼬리표" 순서. 꼬리표는 결품·주의·과잉 구역에서만 떼어 낸다 — 실행 결과 문장은 " · "가 문장 중간에 있다.
  8. **"수신 이벤트 · 개발 상세" 접이식 목록을 화면에서 뺐다**: 사용자가 볼 필요가 없다. 진행 표시(상태 한 줄)와 승인 카드는 그대로다. 이벤트는 DB(`task_event`)와 `GET /api/ai/tasks/{id}`로 볼 수 있다.
- **버린 안**: 화면에 마크다운 렌더러를 붙이기 — 라이브러리 추가와 HTML 주입 방지가 필요하고, 숫자가 틀리는 문제는 그대로다. 프롬프트만 고치기 — 위처럼 지켜지지 않았다.
- **C 파트 코드를 B가 고쳤다** (사용자 지시): `agent/graph.py`의 답변 조립 부분과 `prompts/impact.md`·`qa.md`. 그래프 흐름(노드·분기)은 건드리지 않았다. C의 테스트(단위 18 + 통합 15)가 그대로 통과한다.
- **남은 것 (C)**: 검색 근거의 관련성. SC2 스위치 질문에 도어센서 설계변경 문서가, SC1 MCU 질문에 릴레이 계약이 붙었다. 검색 상위 몇 개를 확인 없이 붙이는 것으로 보인다.

### 6.28 승인 대기함: 팀장 외에는 내가 요청한 카드만 (10/21, 사용자 지시)

- **무엇**: 전에는 대기함 API가 팀장 전용이라 구매 담당자는 자기가 올린 승인 요청이 어떻게 됐는지(대기·거절·실행 완료) 볼 길이 없었다. 이제 팀장은 전부, 다른 역할은 **자기가 요청한 카드만** 본다. 승인·거절 버튼은 그대로 팀장만이다.
- **거르는 곳은 backend** (`Approvals.list`의 `requested_by = 나`, 카드 하나는 남의 것이면 403): 화면에서만 거르면 API를 직접 부르는 사람에게 남의 카드(금액 포함)가 보인다. 금액은 기존대로 보는 사람의 역할에 맞춰 가린다.
- **생산관리**: 승인 요청 자체를 못 하므로 늘 빈 목록이다. 빈 화면에 "발주 변경 요청은 구매 담당자가 한다"는 안내를 넣었다.
- **버린 안**: 같은 팀(구매)끼리는 서로의 요청도 보기 — 요청이 "누구 것도 아닌 공용 목록"이 되면 팀장 대기함과 겹친다. 사용자는 "다른 사용자가 올린 건 안 보이게"로 정했다.
- 기획안 2.3 "작업 기록 보기"(생산관리는 내 것만)와 같은 원칙이다.

### 6.29 여러 품목을 먼저 준비하고 개별 승인한다 (AI·프론트, 10/21, C 파트)

- **요청**: 첫 부품의 팀장 승인을 기다리는 동안 다른 부품 해결안 준비가 막히는 병목을 없앤다. backend 변경 없이 구현하고, 거절 의견으로 새 수량을 만드는 기능은 보류한다.
- **그래프**: 각 대상의 후보 비교·검증·근거를 먼저 완료하고 `proposals`에 저장 → 조합 검증 → 기존 `APPROVAL_REQUIRED`로 각각 등록 → 하나의 결정 대기 노드. 결정을 approval ID로 해당 제안에 연결한다. 등록 순서와 승인 순서는 무관하다.
- **독립성**: 미승인 안을 이미 실행한 것으로 가정하지 않는다. 같은 PO를 변경하는 두 안은 동시에 올리지 않는다. 조합 검증만으로 모든 부분 승인이 안전하다고 보지 않으며 실행 직전에 다시 검증한다. 불일치는 해당 건만 보류한다.
- **영구 접수**: agent는 PostgreSQL에 시작/결정을 기록하고 202를 반환한다. 같은 thread는 DB session lock으로 하나씩 처리한다. RabbitMQ·backend HTTP 경로는 유지한다. `AGENT_DB_URL` 없는 메모리 접수는 지원하지 않는다.
- **복구**: 등록 결과 binding, 실행 전 attempt와 성공 응답, 진행 outbox를 agent 스키마에 둔다. 성공 응답이 저장됐으나 그래프 checkpoint가 미완료면 응답을 재사용한다. 응답 자체가 불명확하면 다시 실행하지 않고 확인 필요로 남긴다.
- **정직한 한계**: backend는 등록 중복 제거가 PENDING에만 있고, 개별 실행 보류 상태 API가 없다. 응답 유실 뒤 완전 자동 복구를 약속하지 않는다. 모호한 건은 수동 대조가 필요하고 작업은 종료하지 않는다. backend가 전체 작업을 FAILED로 끝내면 agent에 전달되지 않은 결정을 이 변경만으로 복구할 수 없다.
- **화면**: 작업별 카드 그룹, 카드별 승인/거절 접수, 승인 목록만 3초 간격으로 갱신, 선택한 카드 최신 상태 반영, 실제 근거 표시. 구매 요청자의 패널은 SSE 재구독으로 이어 보고, 팀장은 다른 사람 작업의 최종 결과를 GET으로 확인한다.
- **한도**: 일반 모델 경로 8턴은 유지하고 다건 ADJUST는 64턴으로 확장한다. active command 구간 600초·그래프 600단계, 대상 10개·총 proposal 30개. 인간 승인 대기에는 타임아웃을 걸지 않는다. 검증 재시도 및 거절 재제안 한도는 대상별로 적용한다.
- **적용 전**: 예전 단일 승인 그래프로 대기 중인 작업은 예전 버전에서 마무리한다. 구형 checkpoint를 새 그래프로 강제 이어가거나 업무 DB를 초기화하지 않는다.

### 6.30 ✅ 거절 뒤 "줄이기만 하는" 부분 해결안은 내지 않는다 — 대안 없음으로 안내 (10/21, 사용자 결정)

- **배경**: SC3에서 팀장이 옛 케이스(CASE-DOOR-V1) 발주 취소안을 "입고 취소 불가, 입고 수량 수정 가능"으로 거절하면 다른 대안이 없다. `compare_options`는 대상 문제를 **푸는** 안만 내는데(6.14), 12/1부터 옛 케이스를 쓰는 생산이 없어 수량을 줄여도 남는 양이 전부 과잉이다. 그래서 취소 외 해결안이 계산되지 않는다.
- **결정**: 계산 엔진은 그대로 둔다. 거절 뒤 대안이 없으면 AI가 그 품목을 **"대안 없음 + 사유 + 다음 행동(담당자가 수량 조건 검토)"**으로 안내한다. 새 수량은 AI가 거절 사유를 읽고 지어내지 않는다.
- **근거**: "푸는 안만 낸다"를 깨면 추천·검증 기준(`resolves`)이 흔들린다. 부분 해결안은 승인 후에도 과잉이 남아, verify가 매번 실패하거나 기준을 따로 둬야 한다. 감량 폭(MOQ까지? 다음 생산분까지?)도 회사 판단이라 시스템이 정할 근거가 없다. C도 "거절 의견으로 새 수량 후보를 만드는 기능은 보류"로 두었다.
- **버린 안**: `OptionAnalysis`에 "MOQ까지 감량" 같은 부분 해결 대안 추가 — B 작업, 6.14 규칙 변경, verify 기준 추가가 필요하다. 시연에서 필요해지면 다시 연다.
- **구현 (B, 사용자 지시 — 원래 C·A 몫)**
  - agent: 거절한 제안에 `outcome`을 붙인다 — 재제안이 저장되면 `REPROPOSED`, 미시도 후보가 없으면 `NO_ALTERNATIVE`, 도구·검색 오류나 거절 후 재분석 실패면 `REVIEW_FAILED`, 거절 횟수·제안 수 한도면 `LIMIT`. 품목 이름·안내·다음 행동·오류 상세를 같이 담는다. 이 칸은 `PROPOSAL_PROGRESS` 이벤트와 `DONE.result.proposals`에 그대로 실린다. 답변의 "거절·보류 결과" 구역도 내부 키(`INV-003|CASE-DOOR-V1`) 대신 부품 이름과 이 문장으로 쓴다. 기존 `blocked_targets`는 그대로 둔다.
  - backend: `GET /api/ai/tasks/{id}`에 `progress`(제안별 최신 진행 이벤트)를 붙였다. 처음엔 화면이 `DONE.result`만 읽게 하려 했지만, 카드 여러 장 중 일부가 아직 대기 중이면 작업이 끝나지 않아 거절 카드의 결과를 볼 수 없었다. 이벤트는 이미 DB에 있으니 읽기만 더하면 된다. 목록 API에는 넣지 않았다(50건마다 읽게 됨).
  - 화면: 승인 대기함의 거절 카드 바로 아래 줄에 결과 표시. 색은 빨강 = 검토 실패(다시 요청), 노랑 = 대안 없음·한도(사람이 조건 검토), 초록 = 재제안(바로 아래 새 카드). 팀장과 요청자 모두 본다(요청자는 자기 카드만, 6.28).
  - 버린 안: 결과를 backend 승인 카드(DB)에 저장 — 사람의 결정 기록에 AI 판단을 섞게 되고 새 내부 API가 필요하다.
- **확인 (실제 모델, 새 DB)**: ① SC3 옛 케이스 취소 거절("입고 취소 불가. 입고 수량 수정 가능") → 대안 없음 ② SC1 분할 거절 → 재제안 생성 + 바로 아래 "전량 당기기" 새 카드 ③ SC2에서 rag-mcp를 멈추고 전원 모듈 분할 거절 → 검토 실패(오류 상세 포함), 같은 작업의 플러그 케이스 감량·릴레이 분할은 실행 완료. 셋 다 다른 카드가 대기 중일 때도 바로 보였다. 테스트: agent 단위 4개 추가(분류·이름·다른 품목 영향 없음), backend 1개 추가(`progress`), C의 기존 통합·복구 테스트 전부 통과.
- **남은 것**: 다른 카드가 대기 중이면 작업 상태가 `RUNNING`으로 보이던 문제는 6.31에서 고쳤다.

### 6.31 카드가 남아 있으면 작업은 "승인 대기"다 (10/21, 사용자 지시)

- **문제**: 작업 상태는 이벤트로 정한다(6.20). 처음 규칙은 "승인 한 번"을 전제로, 팀장이 결정하면 무조건 `RUNNING`(진행 중)으로 바꿨다. 카드 여러 장을 한꺼번에 올리는 흐름(6.29)에서는 첫 결정 뒤 나머지 카드가 팀장을 기다리는데도, 새 `APPROVAL_REQUIRED`가 오지 않아 작업이 계속 "진행 중"으로 보였다. 요청자는 AI가 아직 일하는 줄 알고, 작업 이력의 "승인 대기" 필터에도 안 잡혔다.
- **결정**: 팀장 결정 때 그 작업에 `PENDING` 카드가 남아 있으면 `WAITING_APPROVAL`을 유지한다. 마지막 카드를 결정했을 때만 `RUNNING`으로 넘긴다 (`Tasks.decide`).
- **알고 감수한 것**: 남은 카드가 있을 때 승인한 카드를 AI가 실행하는 몇 초 동안도 "승인 대기"로 보인다. 그 작업에서 사람이 할 일(남은 카드 결정)이 아직 있으니 틀린 표시는 아니다.
- **버린 안**: agent가 처리 단위마다 "지금 상태"를 따로 알려 주게 하기 — 이벤트 종류가 늘고 C·A 계약이 바뀐다. 남은 카드는 backend가 이미 안다.
- 확인: SC2 카드 3장 중 1장 승인 → 승인 대기, 2장째 → 승인 대기, 마지막 → 진행 중 → 완료 (실제 모델). 테스트 1개 추가.

### 6.32 AI 질문의 "선택한 업무"를 사용자가 고른다 (10/21, 사용자 지시)

- **문제**: AI 패널의 "선택한 업무"는 마지막으로 누른 항목을 기억해 보여 주기만 했다. 사용자가 질문하려는 업무를 직접 고를 수 없었고, 업무 없이 묻고 싶어도 지울 수 없었다.
- **결정**: 선택 상자로 바꿨다. 맨 위 **선택 없음**, 아래로 데이터의 **생산계획·발주·자재·제품** 전체를 묶음별로. 화면에서 항목을 누르면 지금처럼 그 업무가 선택된다. 선택 없음이면 질문만 보낸다.
- **보내는 문구는 그대로**(`PP-03 · 스마트 벽스위치`), **보이는 글자만** 날짜·수량을 더한다. 보내는 문구에 "600대" 같은 수량을 넣으면 AI가 질문의 가정 변경으로 잘못 읽을 수 있다 (classify_intent가 질문 전체에서 숫자를 뽑는다). 같은 문구라서 화면 클릭과 선택 상자가 그대로 맞물린다.
- 업무를 바꾸면 이전 답변은 지우지만 **입력 중인 질문 글은 남긴다**. 질문을 쓰고 나서 업무를 고를 수도 있다.
- 결품 항목처럼 목록에 없는 업무를 화면에서 누르면 그 문구가 목록 맨 위에 따로 보인다.
- 확인: PP-03을 고르고 "이 생산을 900대로 늘리면 문제 있어?"라고만 물었더니 AI가 스마트 벽스위치 생산(PP-03)으로 알아들었다 (실제 모델).

### 6.33 구매 담당자가 해결안을 검토해 보낸다 — 초안(DRAFT) 단계 (10/21, 팀 개선안, 사용자 결정)

- **팀 개선안**: 구매가 AI에게 해결을 요청 → AI가 부품당 해결안 1개 → **구매가 메모(개인 판단 + 문제 정의)를 달고 보낼지 결정** → 팀장이 승인·반려 → 반려하면 AI가 사유를 보고 새 안을 바로 제시. 앞뒤는 이미 있었고, 가운데 구매의 검토 단계만 없었다(AI가 카드를 만들면 바로 팀장에게 갔다).
- **결정 (사용자가 추천안대로)**
  1. 구매 요청 카드는 **`DRAFT`로 시작**한다. 요청자가 `submit`(문제 정의·메모)하면 `PENDING`으로 팀장에게, `withdraw`하면 `WITHDRAWN`으로 끝난다. **남의 초안은 팀장에게도 안 보인다.** 팀장은 `PENDING`만 결정할 수 있다.
  2. **반려 뒤 재제안도 다시 초안으로** 구매에게 간다 (버린 안: 팀장에게 바로 — 빠르지만 구매의 메모 없이 올라가 개선 취지와 어긋난다). 별도 코드 없이 "구매 요청 = 초안" 규칙으로 저절로 그렇게 된다.
  3. **팀장이 직접 요청한 카드는 초안을 건너뛴다** — 자기 요청을 자기가 승인할 수 있으므로(1.5) 검토 단계가 같은 사람에게 한 번 더 생길 뿐이다.
  4. **"사유 분석해 새로 나온 방안"은 계산된 후보 중에서 고르는 것**이다(지금 동작). 거절 사유로 새 수량을 지어내지 않는다 (6.30과 같은 이유).
  5. "보내지 않음"은 AI에 `decision: WITHDRAWN`으로 알리고, AI는 그 품목을 재제안 없이 끝낸다. 작업 결과에 "요청자가 보내지 않았습니다 (메모: …)"로 남는다. 다른 카드는 계속 기다린다.
- **문제 정의는 AI가 계산 결과로 미리 채운다** (`problem_text`): "스마트 벽스위치 생산(2026-11-23, PP-03)에 릴레이 400개 부족 · 새 발주로는 늦어 기존 발주 조정 필요". 사람은 고치기만 한다. 빈칸으로 두면 매번 같은 내용을 손으로 쓰게 된다.
- **기록 위치는 backend 승인 카드** (`approval.problem`·`memo`): 사람의 판단이라 업무 기록에 남아야 하고, 팀장 화면이 카드와 함께 읽는다. agent는 메모를 몰라도 된다(결정은 승인·거절로만 받는다).
- **작업 상태**: 초안도 "사람을 기다리는 카드"라 6.31 규칙(남은 카드가 있으면 승인 대기)에 `DRAFT`를 포함했다.
- **화면**: 구매 할 일에 "승인 요청 보내기 (초안)", 승인 대기함에 "검토 전 (초안)"·"보내지 않음" 상태와 필터, 초안 상세에 문제 정의·메모 입력과 [보내지 않음]/[팀장에게 승인 요청], 팀장 카드 상세에 "요청자 검토". AI 패널의 구매 카드는 "요청 준비됨 · 승인 대기함에서 메모 달고 보내기".
- **DB 구조가 바뀌었다** (`approval.status` 값 2개, 칸 2개): 기존 DB는 `docker compose down -v` 후 다시 띄우고 색인을 다시 돌린다.
- **확인 (실제 모델, 새 DB)**: SC2 → 초안 3장(팀장에게 0장) → 릴레이는 화면에서 메모 달아 요청, 전원 모듈도 요청, 플러그 케이스는 보내지 않음 → 팀장은 2장만 결정 대상, 메모 확인 → 릴레이 승인·실행, 전원 모듈 반려 → 재제안이 구매 초안으로 돌아옴(팀장에겐 아직 안 보임) → 구매가 보내고 팀장 승인 → 완료 (실행 2 · 반려 1 · 보내지 않음 1). 테스트: backend 2개 추가·수정, 통합 시나리오 `draft` 추가, 기존 통합 테스트는 초안을 먼저 보내도록 수정.

### 6.34 요청자 검토는 AI 채팅창에서 바로 한다 (10/21, 사용자 지시)

- **무엇**: 6.33의 "메모 달고 보낼지 결정"을 AI 채팅창 안에서 한다. AI가 해결안 카드를 올리면 채팅창의 카드마다 문제 정의(AI가 채움)·메모 입력칸과 [팀장에게 승인 요청] / [보내지 않음]이 붙는다. 보내면 카드가 "팀장 승인 대기"로, 보내지 않으면 "보내지 않음"으로 바뀌고 보낸 메모가 카드에 남는다.
- **근거**: 팀 개선안의 흐름이 "AI에게 묻는다 → 답을 보고 → 그 자리에서 메모 달아 보낸다"였다. 6.33에서는 승인 대기함으로 옮겨 가야 해서 대화가 끊겼다.
- **승인 대기함에서 하는 길도 남긴다**: 나중에 다시 열어 보내거나, 여러 작업의 초안을 한꺼번에 볼 때 쓴다. 두 곳 모두 같은 API(`/api/approvals/{id}/submit|withdraw`)와 같은 상태 저장소를 써서 한쪽에서 보내면 다른 쪽에도 바로 반영된다.
- 채팅창은 카드가 초안인지 backend 상태로 판단한다. 이벤트를 받는 순간 승인 목록을 다시 읽고, 아직 목록에 없으면 요청자 역할로 짐작한다(구매 = 초안, 팀장 = 승인 대기).
- 확인: 구매 계정으로 "허브를 12/14에서 11/25로 당기면 부족한 MCU 어떻게 해결할까?" → 채팅창 카드에 문제 정의가 채워져 나옴 → 메모 입력 → [팀장에게 승인 요청] → 카드 "팀장 승인 대기" → 팀장 카드 상세의 요청자 검토에 같은 문제 정의·메모.

### 6.35 AI 채팅창을 일반 채팅처럼 — Enter 전송, 보낸 질문 말풍선 (10/21, 사용자 지시)

- **Enter = 전송, Shift+Enter = 줄바꿈.** 한글 조합 중(`isComposing`)의 Enter는 글자 확정이라 보내지 않는다 — 막지 않으면 끝 글자가 잘리거나 두 번 전송된다.
- **보내면 입력칸을 비우고, 보낸 질문을 말풍선으로** 답변 위에 보여 준다. 예전 작업을 다시 열면 그 작업의 질문이 말풍선으로 나온다. 접수에 실패하면 쓴 글을 입력칸에 돌려놓는다.
- **앞의 작업이 진행·승인 대기 중이어도 새 질문을 보낼 수 있다.** 전에는 작업이 끝날 때까지 전송 버튼이 막혀, 승인 대기 작업을 보던 중에는 새로 물을 수 없었다. 접수 중일 때만 막는다. 이전 작업은 서버에서 계속 진행되고 작업 이력·승인 대기함에서 다시 열 수 있다.

### 7.2 🟡 이미 낸 발주를 당길 때: 리드타임은 **그 발주의 발주일**부터 센다

- **결정**: `request_due_date_change`·`split_po`의 리드타임 검사를 `new_due_date ≥ max(발주일 + 리드타임, 오늘 + 1일)`로 한다 (3.3의 3번).
- **처음 규칙의 문제**: `오늘 + 리드타임`으로 보면 MCU(56일)는 12/28 전에는 어떤 발주도 당길 수 없다. 기획안의 발주 31건은 전부 "생산 3일 전 도착"에 맞춰 냈기 때문에, 이 기준이면 **기존 발주를 당기는 해결안이 하나도 통과하지 못한다.** SC1·SC4 시연이 성립하지 않는다.
- **근거**: 협력사는 발주일부터 만들기 시작했다. 발주일 + 리드타임이 지났으면 물건은 물리적으로 준비될 수 있다. 아키텍처 1.2의 LT-001도 원래 "**발주일** + 리드타임 ≤ 필요일"이다 — 3.3을 적을 때 "오늘"로 잘못 옮긴 것이다.
- **당기는 데 드는 돈은?** 막지 않고 `compare_options`의 `added_cost`(당긴 개수 × 당긴 일수 × `expedite_cost_per_day`)로 드러낸다. 3.4(MOQ)와 같은 "막는 대신 비용으로" 방식이다.
- **새 발주는?** 발주일이 오늘이므로 그대로 `오늘 + 리드타임 ≤ 필요일`이다. 이게 `analyze_impact` 결품 항목의 `orderable`(contracts 2.2)이다.
- **C 파트 영향**: 같은 오류 코드가 덜 자주 날 뿐이라 코드 변경은 없다. 다만 프롬프트에서 "리드타임이 길어서 당길 수 없다"고 설명하지 않게 확인이 필요하다.
