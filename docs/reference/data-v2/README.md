# 가온스마트 상세 목데이터 v2

이 `data/` 폴더를 기존 git 프로젝트의 `frontend/`, `backend/`, `agent/`, `business-mcp/`, `rag-mcp/` 옆에 넣습니다.

## 파일별 용도

| 파일 | 들어 있는 데이터 |
|---|---|
| seed.json | 기존 DB 컬럼에 맞춘 협력사·품목·BOM·재고·생산계획·발주·ECN·사용자 |
| company_master.json | 회사·사업장·창고 위치·생산라인·고객사·협력사 담당 정보·품목 상세 규격 |
| operations.json | 재고 로트·재고 원장·입고 검수·발주 상세·예정 입고·고객주문·작업지시·생산 상세·BOM 공정 |
| cost_grade_policy.json | 사내 A/B/C/D 비용등급 및 검수 기준 |
| resolution_options.json | 해결안·견적·구매 검수·입력 등급·생산관리 우선순위·잔여 위험 |
| scenarios.json | SC0~SC4 변경 조건·변경 통보·기대 결과·추가 발주안 |
| documents.json | 검색 문서 ID·버전·프로젝트 기준 원문 경로 |
| docs/ | 가상 구매규정·평가규정·협력사 계약·설계변경 원문 6개 |

`seed.json`은 기존 스키마 컬럼을 유지했습니다. 추가 상세 데이터는 `item_id`, `po_id`, `plan_id` 등으로 연결합니다. 문서 원문은 `documents.json`의 경로를 따라 색인하면 됩니다.

현재 git은 고정 응답을 쓰는 뼈대입니다. 파일을 넣은 뒤 backend에서 읽도록 연결해야 화면에 반영됩니다. Docker에서 읽을 때는 `data/` 경로를 마운트하거나 빌드에 포함합니다. 이 ZIP에는 별도 실행 프로그램이나 검증 폴더가 없습니다.

## 가온스마트에 맞춘 상세 정보

- 스마트 플러그·2구 벽스위치·도어 센서·IoT 허브의 내부 모델과 공칭 규격
- 3개 협력사의 공급 범위·가상 담당자·거래조건·납품 방식
- 단일 창고 안의 ESD·전자자재·기구포장·완제품·검수대기 구역
- 현재 재고와 정확히 맞는 로트 46건 및 재고 이동 46건
- 입고 완료 MCU 300개의 수량·검수·재고 반영 기록
- 미입고 발주 31건의 납기 확약·예정 운송·미검수 상태
- 생산계획 7건과 연결되는 고객주문 7건·작업지시 7건
- 해결안 13개의 비용 근거·구매 검수 체크·입력 등급·생산관리 우선순위

회사와 거래처, 담당자, 연락처, 제품 규격과 계약은 모두 가상입니다. 이메일은 실제 발송되지 않는 `example.invalid` 주소입니다. 실제 사업자번호·주소·인증번호는 만들지 않았습니다.

## 기준과 시점

기준 스냅샷은 **2026-11-02 09:00**입니다. 검수·우선순위 예시는 각 시나리오에서 이후 10:00~11:00에 진행한 독립적인 목상태입니다. SC1~SC4를 기준 데이터에 동시에 덮어쓰지 않습니다.

기획서의 완제품 4종·반제품 6종·구매부품 28종·협력사 3곳·생산계획 7건, 모든 초기재고·안전재고, 미입고 31건의 수량·날짜와 12/1 도어센서 케이스 설계변경을 보존했습니다. 완제품 출하대기 재고는 총 **390대**이며 생산계획에서 다시 차감하지 않습니다. 반제품 재고는 없습니다.

내부 BOM 연결은 66행입니다. 원본 스키마 요약의 65행과 차이가 있지만, 제품별 말단 소요량·허브의 구매부품 16종·최대 3단계 깊이는 맞췄습니다. 원문에 내부 연결표와 실제 회로도가 없으므로 이번 연결은 합성 구조입니다.

캐패시터·저항·나사·일부 포장재는 원문대로 여러 규격을 묶은 집계 SKU입니다. `is_aggregate_demo_sku`에 표시했습니다. 실제 양산 BOM이나 인증·설계 자료로 쓰는 규격은 아닙니다.

## 새로 만든 가정

원문에 없는 단가·품목 규격·포장 단위·MOQ·수수료·고객주문·로트·거래조건은 목값입니다. 품목별 MOQ는 캐패시터/저항 1,000개, LED 500개, 나사 300개, 나머지 구매품목 100개입니다. 발주배수는 모두 100개입니다. 현재 발주 및 시나리오 추가 발주 수량이 이 조건을 만족합니다.

운송 포장단위와 MOQ는 다르며 부분포장을 허용합니다. 기준 캘린더는 원문에 있는 주말 입고일도 허용합니다. 1월 입고 발주는 기준일 이전의 선발주로 기록했습니다.

기초 로트의 이월 이전 전체 ERP 이력을 새로 꾸미지는 않았습니다. 재고 원장은 기초이월과 수록된 입고로 완결됩니다. MCU 과거 입고 300개는 현재 2,700개에 이미 포함됩니다. `goods_receipts`와 `stock_movements`를 동시에 더하면 중복입니다.

미래 입고를 실제 도착·검수 완료로 표시하지 않았습니다. 기준 시나리오에서 보류재고와 불량은 0입니다. 고객주문과 작업지시는 생산계획을 설명하는 부속 데이터이므로 BOM 소요에 중복 합산하지 않습니다. 기존 완제품 390대는 이 7건의 미생산 주문에 배정하지 않은 출하대기 재고입니다.

## 구매 검수와 생산관리 우선순위

비용등급은 가상 사내 정책입니다. 부가세 제외 KRW 기준으로 A는 0~49,999원, B는 50,000~199,999원, C는 200,000~499,999원, D는 500,000원 이상입니다.

정상 구매원금과 기존 재고 평가금액은 추가비용에 포함하지 않습니다. 미확정 손실은 null이며 0원으로 확정하지 않습니다. 고객 납기 변경의 미확정 손실은 별도 위험으로 기록했습니다.

구매 담당자가 검수한 확정 등급만 생산관리에게 전달합니다. 실제 금액·견적·비용명세는 생산관리 AI에 전달하지 않습니다. 생산관리는 납기·다른 제품 영향·잔여 위험을 함께 보고 별도로 순위를 정합니다. 생산관리 선정 뒤에도 구매 요청과 팀장 승인이 있어야 발주를 변경합니다. 미검수·반려·대체된 후보에는 확정 등급과 생산 우선순위가 없습니다. 미해소 결품 후보는 실행안으로 선정하지 않습니다.

시연용 사람 검수·견적·우선순위 기록은 실제 직원이 입력한 기록이 아닌 목데이터입니다. 사용자 계정은 로그인 비활성 상태입니다.

SC2에는 원본 PRD가 빠뜨린 나사 600개·버튼 캡 300개·중형 박스 300개의 추가 소요도 포함했습니다. SC2/SC3의 추가 발주는 해결 제안이며, 이미 입고된 것으로 계산하지 않습니다.
