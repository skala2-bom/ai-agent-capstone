# 작업 단위 구매 검토 변경 기록

2026-10-21 · 로컬 구현. 커밋·푸시하지 않음.

## 사용자 흐름

1. 박구매가 AI에 해결안을 요청한다. AI가 각 부품의 고정된 문제와 해결안을 모두 준비한다.
2. 채팅 또는 승인 대기함의 연한 연두색 작업 카드에 **전체 문제 설명**을 작성한다. 각 부품에는 **개인 메모**를 입력한다.
3. 작업 카드의 **팀장에게 승인 요청**을 누르면 현재 초안 전체가 한 번에 전달된다. **보내지 않음**도 현재 초안 전체에 적용한다.
4. 팀장은 전체 문제·품목별 문제·개인 메모를 확인하고 **부품별로 승인·거절**한다. 승인한 것만 기존 흐름으로 실행한다.
5. **추가 변경(6.37):** 팀장 거절 후 재제안은 구매 재검토 없이 팀장 승인 대기로 바로 전달된다. 기존 전체 문제·구매 메모를 이어받으며, 실행은 새 제안에 대한 팀장 승인을 기다린다.

작업 카드에는 원 질문을 표시하지 않고 전체 문제 설명만 표시한다. 작업은 최신순이고 작업 내부의 기존 순서·거절 바로 아래 재제안 배치를 유지한다. 임시저장 API나 자동 저장은 없다. 아직 보내지 않은 입력은 같은 탭의 메모리에만 있으며 새로고침하면 사라진다.

## 백엔드·DB 변경 범위

- 운영 Java 코드는 **Approvals.java·Tasks.java 두 파일**만 변경했다.
- **DB 스키마·마이그레이션 변경 없음.** `approval.problem`은 그대로, 기존 `approval.memo`에 버전이 붙은 JSON 문자열을 저장한다.
- JSON에는 전체 문제 설명, 개인 메모, 멱등 요청 ID·회차·결정이 들어간다. 화면 API는 이를 분리해서 반환하므로 사용자에게 원시 JSON은 보이지 않는다. 이전 일반 문자열 메모도 읽는다.
- 새 경로: `POST /api/ai/tasks/{taskId}/review/submit|withdraw`. 현재 작업의 **모든 DRAFT**를 처리한다. 팀장 승인·실행은 기존 API와 인자를 유지한다.
- 전송 중 에러가 발생하면 일부만 처리되지 않도록 트랜잭션으로 되돌린다. 네트워크 응답 유실은 같은 요청 ID로 확인한다.
- 철회는 DB에 먼저 저장한다. 대기열 연결이 끊겨도 주기적으로 미확인 WITHDRAWN을 재전송하며, agent의 WITHDRAWN 진행 확인 뒤 멈춘다. 실제 실행 도구는 부르지 않는다.
- 이전 프론트의 카드별 전송 API는 사용할 수 없다. agent·backend·frontend를 함께 재빌드해야 한다.

## 최초 작업 단위 검토 구현에서 확인한 테스트

- 백엔드: 37개 통과(기존 29개 + 작업 검토 8개). 실제 격리 PostgreSQL 사용. 일부 UPDATE 실패 시 전체 롤백과 동시에 전송/철회했을 때 하나만 성공하는 경우 포함.
- 프론트: 41개 통과, TypeScript 검사·프로덕션 빌드 통과.
- agent 승인 러너: 14개 통과. 실제 격리 체크포인트 DB 사용.
- 통합: 골든 계산 8종, SC1~4 분석→검토→승인→실행, 거절 후 재제안, 혼합 개별 결정, 작업 전체 전송/철회, SYSTEM 지연 분석, 문서 QA 통과.
- 실제 Chrome 화면: 채팅·승인 대기함 입력 공유, 작업당 전송 버튼 1개, 고정 품목 문제, 팀장 상세의 전체 문제·메모, 전체 철회 후 팀장 비노출을 확인했다. 브라우저 오류 없음.
- 모델·검색은 결정적 테스트 대역을 사용했다. 이번 검증에서 실제 OpenAI 모델은 호출하지 않았다.

검증은 별도 `capstone-task-review-test` Compose 프로젝트와 Testcontainers에서 수행했다. 기존 `ai-agent-capstone` 개발 컨테이너·DB는 변경하지 않았다.

## 로컬 화면에서 확인하기

저장소 루트에서 실행한다. DB 삭제는 필요 없다.

```bash
docker compose up -d --build agent backend frontend
```

브라우저를 새로고침하고 박구매로 로그인한다. 기존 초안도 agent가 저장된 상태를 확인한 뒤 준비 신호를 복구한다.

예시 질문:

> 11/23 스위치 생산을 900대로 늘리고 11/30 플러그 생산은 500대로 줄이면 어떻게 돼? 결품과 과잉 해결 방법 만들어 줘.

- 전체 문제: `스위치 증산과 플러그 감산으로 생긴 결품·과잉을 함께 해결해야 합니다.`
- 각 부품 메모: 협력사 확인 내용·내 판단을 서로 다르게 입력한다.
- 전송 전 팀장에게 안 보이는지, 한 번 전송하면 전체 문제와 메모가 함께 보이는지 확인한다.
- 별도 작업에서 보내지 않음을 누르고 모든 초안이 WITHDRAWN인지, 팀장에게 작업이 안 보이는지 확인한다.
- 팀장의 승인·거절은 여전히 부품별로 가능하며, 이전 실행 결과는 다시 보내지지 않는다.

이전 테스트로 발주가 이미 바뀐 개발 DB에서는 같은 질문에 대한 카드 수·대안이 달라질 수 있다.

## 추가 변경: 거절 재제안 직접 전달 (6.37)

- 사용자 추가 허용에 따라 **Approvals.java의 재제안 분기만** 수정했다. 이번 변경에서 Tasks.java·DB 구조·DB 초기화 파일은 그대로다.
- `agent/graph.py`: 재제안 이벤트에 이전 거절 승인 ID를 명시한다.
- `agent/approval_runner.py`, `agent/approval_store.py`: 업데이트 전 등록된 재제안 초안도 저장된 카드 ID로 복구한다. 구매 화면이 닫혀 있어도 동작하며, 새 카드 중복 생성이나 자동 발주 실행은 하지 않는다.
- `frontend/src/views/Approvals.vue`: 원 질문을 숨기고 전체 문제만 표시한다. 기존 구매 메모는 재제안 상세에서 "이전 요청의 구매 메모"로 표시한다. 이전 카드 ID를 기준으로 재제안을 바로 아래 배치한다.
- 프론트 API/타입에 `previousApprovalId`를 연결했다. backend 응답에 없는 이전 기록은 기존 제목 연결 방식으로 표시한다.
- 최초 제안의 작업 단위 구매 검토는 그대로다. 재제안만 PENDING으로 바로 전달하며 팀장의 부품별 승인·거절·실행 흐름을 유지한다.
- 기존 일반 텍스트 메모는 계승하되, 없는 전체 문제 설명을 원 질문으로 대체하지 않는다.
- 적용 시 agent·backend·frontend를 함께 재빌드한다. 이미 등록된 재제안 초안은 agent 시작 시 또는 이후 약 30초 주기의 복구 검사에서 전환된다. 등록 결과가 불명확해 보류된 카드는 자동 전환 대상이 아니다.

### 재제안 변경 검증

- 백엔드 관련 테스트 26개 통과: TaskReviewTest 12개, ApprovalFlowTest 7개, TasksTest 7개. 최초 제안 DRAFT 유지, 거절·동일 품목 검증, 메모 계승, 중복 등록 방지, 이미 결정된 카드 상태 보존 포함.
- 프론트 테스트 42개 및 TypeScript 검사·프로덕션 빌드 통과.
- agent 승인 러너 17개 통과. 기존 재제안 초안의 정확한 카드 ID 복구, 응답 유실 시 같은 카드 재시도, UNKNOWN 등록 재전송 금지 포함.
- 통합 `reject`, `mixed`, `draft`, `SC1`~`SC4` 통과. 재제안에서는 구매 전송 API를 호출하지 않고 팀장 조회만으로 수신을 확인했다. 팀장 승인 전 변경 이력이 없는지도 확인했다.
- 실제 Chrome에서 최초 전송 후 구매 브라우저를 닫고, 팀장 화면에서 거절 → 재제안 직접 수신 → 승인 → 실행 완료까지 확인했다. 작업 카드의 원 질문 비노출, 전체 문제·이전 메모 계승, 거절 카드 다음 재제안 배치와 브라우저 오류 없음도 확인했다.
- 이번 테스트는 별도 `capstone-reproposal-test` 프로젝트에서 실행했다. 실제 모델 호출 없이 테스트 대역을 사용했으며 개발 컨테이너·DB는 변경하지 않았다.
