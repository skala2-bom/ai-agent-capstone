# 입고 지연의 대상·기간 추출

현재 OPEN 발주 목록 (실제 기존 입고일 기준):
{RECEIPTS}

- 입고가 늦어졌거나 늦어지는 가정이면 `receipt_delays`에 추출한다. 같은 발주를 `whatif`에 중복 기재하지 않는다.
- 사용자가 발주 번호를 말했으면 `po_id`, 그렇지 않으면 목록의 `item_name`을 쓴다. 와이파이칩 = Wi-Fi 칩.
- 원래 날짜를 명시했을 때만 `original_due_date`를 채운다. 목록에서 임의로 발주 하나를 골라 번호를 만들지 않는다. 같은 부품 발주가 여러 개면 코드가 후보를 확인한다.
- "11/13 입고가 일주일 늦어졌다" → 원래 입고일 2026-11-13, delay_days=7, new_due_date=null. 날짜 덧셈은 코드가 기존 due_date에 수행한다.
- "11월 27일로 늦어진다" → new_due_date=2026-11-27, delay_days=null. 날짜를 지정하지 않은 "약 1주"는 분석용 7일이며 확정 통보로 취급하지 않는다.
- 발주 번호와 새 입고일이 명시되면 그 발주 한 건의 날짜 변경을 추출한다. "최초 예정일 기준 총 4주, 새 입고일 12/25"처럼 과거 기준을 설명하는 날짜는 현재 OPEN 발주를 찾는 original_due_date에 넣지 않는다. 이 경우 original_due_date=null, new_due_date=2026-12-25, delay_days=null이다. 저장된 날짜에 다시 4주를 더하지 않는다.
- "릴레이 입고일이 11월 20일에서 11월 27일로 늦어지고, 와이파이 칩은 11/13에서 11/20로 늦어진대. 생산에 어떤 문제가 생겨?" → IMPACT, receipt_delays 2건: 릴레이(original_due_date=2026-11-20, new_due_date=2026-11-27), Wi-Fi 칩(original_due_date=2026-11-13, new_due_date=2026-11-20). 둘 다 delay_days=null. 날짜 차이를 7일로 계산해서 채우지 않는다.
- 입고 지연에 따른 생산 영향은 기존 생산계획으로 계산한다. 사용자가 생산계획 자체를 바꾸겠다고 하지 않았다면 새 생산일·제품을 추가로 요구하지 않는다. 부품명과 원래 입고일로 발주가 특정되고 새 입고일도 있으면 unclear=null이다. 다른 미확정 조건이 실제로 있을 때만 대상·필요한 정보를 unclear에 적는다.
- 서로 다른 두 발주의 지연은 두 건으로 추출한다. 기간을 임의로 보태거나 스트레스 시나리오를 만들지 않는다.
- "더 길어지면/장기화되면"도 비교해 달라고 하면 해당 receipt_delays 항목에 may_extend=true를 붙인다. 그 표시를 위해 whatif에 같은 발주를 중복 작성하지 않는다. 1·4·12주 비교 날짜는 코드가 생성하며 통보 기준 새 입고일을 덮어쓰지 않는다.
- "문제 있나?"는 IMPACT. 실제 발주·생산계획 변경이나 요청 전송은 별도 사용자 확인을 거친다.
